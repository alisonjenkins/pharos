# Invariants — pharos baseline

Normative register. Migrated verbatim from `SPEC.md` §V on 2026-07-27. These are
the non-negotiable properties every plan and change is checked against (see
`.specify/memory/constitution.md` → Governance). Numbering (V1…V81) is stable and
load-bearing — tasks, bugs and code comments cite these ids. Never renumber; append.

- V1: unmodified Jellyfin client connects, browses library, plays media (direct + transcoded).
- V2: unmodified Plex client connects, browses library, plays media (direct + transcoded).
- V3: group session syncs play/pause/seek across members within 500ms p95.
- V4: HTTP handler never panics. Errors return structured response matching target API schema.
- V5: library scan never blocks playback or API requests. Scan runs in dedicated task pool.
- V6: ffmpeg subprocess crash never crashes server. Failed transcode returns error to client.
- V7: API response shapes match Jellyfin/Plex reference schemas byte-equivalent for shared fields.
- V8: auth tokens never logged. Secrets redacted in all log output.
- V47: a response to a Range request that carries Content-Range is 206, never 200 (Firefox `<video>` `bytes=0-` open probe must confirm seekability).
- V9: media file path never leaks to unauthenticated client. Path traversal blocked at boundary.
- V10: store writes atomic per logical op. No partial library entry visible to readers.
- V11: every public behavior covered by test written before impl (TDD). No merge without failing-test-first evidence.
- V12: trait boundary between domain logic and IO. Domain layer testable without DB/fs/network/ffmpeg.
- V13: every inbound request traced. Every outbound IO (db, ffmpeg, fs walk, http client) spanned. trace_id propagated to logs.
- V14: `/healthz` returns 200 if process alive. `/readyz` returns 200 only when store reachable + scanner initialized. `/metrics` exposes Prometheus format.
- V15: structured logs only. No `println!`/`eprintln!` in non-test code. `tracing` crate sole logging surface. CLI subcommands may write to stdout/stderr via explicit `std::io::Write` (not logging).
- V16: Dioxus UI consumes only public Jellyfin-compat API. No backdoor endpoints. UI swappable for any Jellyfin client.
- V17: no `unwrap()` / `expect()` in non-test code. Enforced via `clippy::unwrap_used` + `clippy::expect_used` = deny at workspace level. Tests may opt-out.
- V18: mutable runtime state owned by exactly one task. Mutation via message-passing (tokio mpsc). No `Mutex<State>` on request path. Locks permitted only for one-shot init or immutable-after-init caches.
- V19: group-sync must improve on Jellyfin SyncPlay failure modes. Specifically: (a) late joiner does not desync existing members; (b) one poor-network member does not stall the group (per-member buffering isolation); (c) leader handoff causes ≤1 corrective Pause, no buffer storm; (d) network blip <2 s reconverges automatically without member rejoin.
- V20: group-sync wire protocol stays Jellyfin SyncPlay-compatible so unmodified phone/TV clients participate. Improvements live in server-side algorithm. A second WS path may carry an extended protocol for pharos-native clients, but the Jellyfin-shaped socket is the canonical entry point.
- V21: SyncPlay server never withholds command client must ACK. Readiness gate waits only on members expected to emit player transition (queue load, already-delivered Seek, active buffering). Plain Unpause of non-buffering group broadcasts immediately. Every SendCommand carries PositionTicks (jellyfin-web seeks to it — missing value = seek to 0). SetIgnoreWait honored: halted member excluded from all gates.
- V22: Quick Connect wire flow matches jellyfin-web two-endpoint exchange. `/QuickConnect/Connect` is read-only poll — echoes `Secret`, reports `Authenticated`, never mints token, never consumes. Finalize at `POST /Users/AuthenticateWithQuickConnect` {Secret} (unauth — secret IS credential): single-shot consume of an AUTHORIZED entry → AuthenticationResult (User + AccessToken). Unauthorized/unknown/spent secret → 401. Its query params (`secret`, `code`) bind case-INSENSITIVELY — mobile/TV SDKs send camelCase, jellyfin-web PascalCase; real Jellyfin (ASP.NET) is case-insensitive, so a case-sensitive extractor 400s non-web clients.
- V23: software video transcode jobs are thread-bounded + speed-preset. Every sw encode AND decode capped at `sw_encode_threads()` (≈4); libx264/libx265 get `-preset veryfast` (never x264 default `medium` — below realtime under load); CPU permit budget = `cores / sw_encode_threads()`, never permits=cores (double-counts: each job auto-threads all cores, all admitted jobs slow below realtime together); prefetch depth derives from permits, capped at 4. Invariant: `permits × threads-per-job ≤ cores`.
- V24: a synth group id (Series/Season/Artist/Album) serves LEVEL-specific art before any representative-member fallback. Seasons: probe the Kodi/Jellyfin series-root sidecars (`season{NN}-poster/-fanart/-banner`, zero-padded + bare, `season-specials-*` for S0) for the season the id names; only then fall back to the representative episode's artwork (series poster). Fallback must never make two different groups of one show serve identical bytes when level-specific art exists on disk.
- V33: the video transcode target codec PREFERS H.264 whenever the client advertises it (`negotiate` picks h264 out of the transcoding profile's `video_codec` CSV, not the first-listed). H.264 is the shareable target: the segment cache key is `(media, seg, audio, sub, bitrate, codec)` with no user/device, so every SyncPlay group member transcoding to h264 hits ONE cached encode. Honouring the client's first-listed codec split a group across encodes — a browser listing `vp9,h264` cold-transcoded its own (software, slow) VP9 while the rest shared a warm h264 stream, so it stalled and never joined shared playback. A client offering no h264 (VP9/AV1-only) still gets its first codec; the Linux-Firefox-can't-decode-h264 case is forced to VP9 downstream (`playback_info` `force_webm`), which overrides this. PlaybackInfo logs the full codec decision (`playbackinfo: codec decision` — is_firefox, client_offers_vp9, force_webm, negotiated codec, route).
- V32: a member's delivery sink in `MemberSinks` is GENERATION-FENCED — every insert/remove carries the owning socket's `conn_gen`. An insert lands only when its gen ≥ the stored gen; a remove fires only when its gen == the stored gen. So no stale writer (the losing task of two racing connects for one deterministic member_id, or an HTTP New/Join re-registering a sink snapshot resolved just before a reconnect) can ever install a dead sink over the live one, and no late disconnect teardown can wipe the sink a fresh reconnect just registered. A blackholed sink = the member silently receives NO SyncPlay traffic until its next reconnect (the "got stuck / never started" failure). The Jellyfin `/socket` path uses the hub's per-device conn_gen; the native `/sync/v1/ws` path uses a process-wide monotonic counter.
- V31: the V19 per-member buffering freeze is BOUNDED — one member's `BufferingStart` may pause the group, but the group ALWAYS resumes. It resumes (a) the moment the last buffering member reports `BufferingEnd`/`Ready`, (b) immediately when the last buffering member LEAVES (socket drop / Leave / ghost-prune) without a `BufferingEnd` — a departing member must never own the freeze — or (c) after `BUFFERING_MAX_MS` (anti-wedge) if a member buffers forever without recovering, ending, or leaving. A group hydrated mid-freeze (rolling deploy) re-arms the anti-wedge deadline, since its restored members carry cleared buffering flags and can never fire the `BufferingEnd` auto-resume on their own. Mirror of V28's readiness-gate anti-wedge, for the buffering path.
- V25: a SyncPlay watch party survives a process restart / rolling deploy end-to-end, and the server NEVER silently drops a group command. Member ids derive deterministically from deviceId (same device → same member id across restarts); on /socket connect with no in-memory membership the server recovers it from the persisted `sync_groups` snapshots and resyncs the client; a command from a session with no recoverable group answers `NotInGroup` over the socket (stock jellyfin-web then visibly disables SyncPlay) — a silent drop lets the sender's local player apply the command one-sidedly (Pause pauses only the presser) and desyncs the party.
- V29: a trickplay sprite set counts as GENERATED only when its per-(media,width) `.complete` marker exists — written strictly after every sheet landed. Tile presence alone is a lie: the libav worker writes sheets straight into the served dir, so an interrupted run (op timeout, worker crash, deploy) leaves a truncated set that must be re-attempted, never advertised (grey previews past the truncation point otherwise). Marker-less sets are verified against the duration-derived expected sheet count (±1 trailing sheet for VFR/rounded durations): consistent → stamp marker; truncated → wipe + regenerate. Whole-file heavy-op timeouts scale with content duration (`max(900s, duration/2)`) — a fixed cap kills long movies partway. Image-subtitle burn-in uses the `overlay` filter_complex (the `subtitles=` filter is text-only and cannot render PGS/VOBSUB).
- V28: SyncPlay command scheduling is BOUNDED and gate ACKs are causally valid. (a) Clock samples with RTT > 10s are discarded at observe time (a throttled/suspended tab measures its own stall, not the network — its offset estimate is garbage too); (b) `lead_time_ms = MIN_LEAD + min(max_rtt/2, 2s)` — one member's pathological RTT must never schedule commands tens of seconds out for the whole group; (c) a readiness gate opened for a SCHEDULED command (Seek: clients execute at `When = at_server_ms`) ignores any `Ready` arriving before `at_server_ms` — it cannot be an ACK of a command nobody has executed yet; it's a spurious player transition. Counting it resolves the gate early, and the resulting Play broadcast makes jellyfin-web's `scheduleUnpause` CANCEL the client's still-pending seek callback (`clearScheduledCommand`), after which nothing ever seeks — `scheduleUnpause` only corrects players AHEAD of target, so everyone silently resumes from the pre-seek position.
- V27: every client-attributed SyncPlay report or request that names a queue entry (`Ready`, `Buffering`, `NextItem`, `PreviousItem` — all carry `PlaylistItemId`) is validated against the CURRENT queue entry before it acts. A stale-entry `Ready`/`Buffering` (the old episode's player transitioning during teardown, racing a queue change) must neither satisfy a readiness gate nor freeze the group — the sender gets a single-member PlayQueue catch-up re-send (same `LastUpdate`, so up-to-date clients drop it as a duplicate) and is expected to re-report for the right entry. A stale-entry `NextItem`/`PreviousItem` is a no-op (double-press / two-member race would skip an episode). jellyfin-web posts `Ready` on EVERY player transition, so an unvalidated gate is trivially poisoned by teardown transitions. Wire `UserLeft` carries the member's display NAME, never the member uuid.
- V30: the segmented-HLS surface (`/hls1/*.ts`) NEVER stream-copies video and never passes multichannel audio. `-c:v copy` per-segment HLS is structurally broken three ways: ffmpeg cuts copy output on source keyframes (durations drift off the uniform EXTINF grid), `-output_ts_offset` is silently INERT under copy (every segment restarts at PTS≈0), and passthrough/re-encoded multichannel AAC is undecodable in Firefox's MSE (fatal append on segment 0 — playback never starts; Chrome tolerates all three, masking the breakage). Every `.ts` segment: re-encoded H.264, `-muxdelay 0 -muxpreload 0` (default 1.4 s mpegts cue delay skews the anchor), `-output_ts_offset <start>`, AAC forced `-ac 2`. Copy remux stays legal ONLY on the progressive `/stream` path (one continuous output, no per-segment cuts). Corollary: any ffmpeg flag doing timeline/mux work needs a BEHAVIORAL test (run ffmpeg, ffprobe the output) — an argv-string assertion passes even when the muxer ignores the flag (B41 shipped exactly that way).
- V31: image-subtitle burn-in pays ONLY for segments the track provably subtitles. Every burn-capable request (live .ts, VP9 init/media, both prefetch paths) gates against the track's scanned event-window timeline (TinyOp::SubtitleWindows — packet demux, no decode; persisted per file+mtime+track via SubtitleKind::EventWindows); an event-free segment window (±500ms pad) strips the burn index, takes the plain fast path, and shares its cache key with subtitle-off playback. Gating is FAIL-OPEN: unknown/in-flight/failed timeline → burn conservatively — it may only remove provably-empty burns, never lose a visible subtitle. A nonexistent track index errors, never returns an empty (= never-burn) timeline. Prefetch re-gates per TARGET segment (the requesting segment's decision does not transfer on a sparse track). Any segment transcoding >3× its content duration logs WARN with full attribution (queue-wait/encode split, device, codec, burn, seek depth, source).
- V26: every server-side UserData mutation (mark played/unplayed, favorite/unfavorite, progress save, stop-finish) broadcasts a `UserDataChanged` frame whose `UserDataList` entries are FULL serialized `UserItemDataDto`s — `ItemId` in canonical 32-hex wire form, `Key`, `Played`, `IsFavorite`, `PlayCount`, `PlaybackPositionTicks`, `PlayedPercentage` (computed from runtime when known). jellyfin-web patches cards by `data-id == ItemId` and the detail page by `Key`, then applies the state fields in place — a bare `{ItemId}` stub or a decimal id matches nothing, so the UI only updates on manual refresh. Synthetic series/season ids cascade the mutation to every child episode and batch all changed entries (+ a folder entry keyed by the synth id) into ONE frame.
- V34: every heavy whole-file / whole-decode media source op (subtitle vtt/ass/srt extract, trickplay sprite generate, waveform astats, image poster/backdrop/attachment/font extract, any ffmpeg/libav source open) acquires a shared `bg_io` permit BEFORE touching the source — enforced by a `BgPermit` token in the fn signature, not by convention (an ungated call must not compile). Background sweeps ALWAYS gate; playback-priority "bypass" work (actively-watched item only, never a sweep) may run hotter but stays batched and yields to the metered live stream.
- V35: EVERY playback delivery path marks playback activity CONTINUOUSLY as bytes flow (metered body / lease refresh), never once-per-request — HLS `.ts`, progressive webm, direct-play + DirectStream `stream.{mp4,mkv}`, resume-from-offset, and all audio (`/audio/{id}/stream|universal`, remux). So the bg_io regulator parks the gate for the ENTIRE stream incl. a single long GET; `is_streaming()` is true for ANY active playback, not just segment-pulling clients.
- V37: `SupportsDirectStream` is advertised ONLY when pharos's verbatim `/stream` file plays as-is for THIS client — a real DirectPlay, or a webm-codec Matroska (VP8/9/AV1 + Opus/Vorbis) `deliver_stream` re-labels to `video/webm` for a client whose profile lists a matching webm DirectPlayProfile. `/stream` never remuxes the container or transcodes audio, so any remux decision whose raw file isn't playable (h264+eac3/ac3/dts Matroska) MUST carry a TranscodingUrl and NOT advertise DirectStream. Err toward transcode (always plays) over DirectStream (may be unplayable).
- V36: per-item asset generation opens the source ONCE per item — all subtitle tracks, all trickplay widths, all font attachments from one file open, never a loop of opens; and every on-demand extract (subtitle vtt/ass/srt, poster/backdrop/attachment/font, waveform) is cached AND single-flighted via a shared fetch-lock (get→lock→get double-check) so a cache miss can't fan into N concurrent whole-file demuxes of the same key. Fixed scratch paths are per-caller-unique. (Cache tier is per-cost: subtitle/image extracts are DISK-backed under the cache PVC — a once-ever cost surviving restarts; waveform is IN-MEMORY-memoised only, since its endpoint is client-optional and recompute is cheap.)
- V38: EVERY Jellyfin wire object a strict SDK (jellyfin-sdk-kotlin) deserializes is emitted from a typed `#[derive(Serialize)]` DTO, NEVER a raw `serde_json::json!` literal — so the kotlin-required-field contract is enforced by the type and a field-missing object cannot be constructed. Especially `/socket` broadcast payloads (`Sessions.Data[].NowPlayingItem`, remote/PlayState pushes), which bypass the audited `/Items` `BaseItemDto` path. Any embedded `BaseItemDto` (even minimal) carries its two no-default kotlin fields `Id` + `Type`; an unresolved `Type` OMITS the nullable item rather than emitting it Type-less.
- V39: A wire field typed as a kotlin ENUM (`PlaystateCommand`, `GeneralCommandType`, `PlayCommand`, …) may ONLY carry a value that is an exact member of that enum. A relayed/remote command whose value is outside the target enum is DROPPED (not forwarded), never emitted as a free string — an out-of-set enum fails the strict `kotlinx.serialization` decode and crashes a native cast TARGET (B79, same class as B78). Corollary: media-play is the dedicated `Play` MessageType (`PlayRequest`), not a `PlayState` `Command:"Play"`; `GeneralCommand` carries a non-null UUID `ControllingUserId` and a `Map<String,String>` `Arguments`.
- V40: No browser client is ever handed an unplayable stream with no fallback. Extends V37 to the DirectPlay VERDICT path: a DirectPlay / `SupportsDirectStream` result for a Matroska-container source to a browser (`<video>`/MSE, Mozilla UA) is honoured ONLY when the verbatim `/stream` relabel is `webm_relabel_playable` (webm-legal video AND audio that the client's profile lists); otherwise `playback_info` downgrades the `Decision` to a Transcode so a `TranscodingUrl` is emitted and SupportsDirectStream resolves false (B80). The B43 `force_webm` net is NOT relied on for this — it is off when `linux_firefox_h264=true` (B60). A genuine `webm` container is trusted (natively browser-playable + client-listed); only Matroska/MKV (the relabel hazard) is gated.
- V41: A client-supplied `ParentId` is matched in pharos's canonical dashless-32-hex wire form. `resolve_parent_filter` and `restrict_to_parent` canonicalise the id (`canonical_parent_id`: strip the dashes of an 8-4-4-4-12 hex UUID and lowercase; every other shape untouched) BEFORE any `== wire_id` / synth-hash / entity-store comparison, so a dashed UUID (jellyfin-sdk-kotlin / Android TV re-serialises every id through a `Uuid` and emits it dashed) resolves identically to the dashless form jellyfin-web echoes. A mismatch here silently falls to `Empty` — a blank library grid, no 4xx (B82). Extends the B15 inbound-id sweep (which canonicalised route-path ids via `parse_item_id` but left ParentId query-param resolution on raw string equality).
- V42: `/Items/{id}/Similar` ("More Like This") lists only items that share a REAL content-overlap signal with the target — same series, album, album_artist, genre, or immediate parent folder. Same media-kind alone is a tiebreak (sorts already-qualified ties kind-first), NEVER a qualifier: `similarity_score` adds its `+5` same-kind bonus only when the real-signal score is already `>0`, and `items_similar` keeps only `score > 0`. A thin-metadata library therefore returns a short or empty rail, never an alphabetical dump of every same-kind item (which surfaced unrelated content — an AWS training clip under "Back to the Future") (B83).
- V46: A movie/episode with NO sidecar `.nfo` still surfaces its embedded container description. The prober (both libav default + spawn) lifts `synopsis`/`description`/`comment` → `MediaProbe.synopsis`, `content_rating`/`rating`/`mpaa`/`law_rating` → `content_rating`, `network`/`publisher`/`studio` → `network`, and the full raw `date`/`originaldate`/`creation_time` → `release_date`; all four persist as `media_items` columns (round-tripped, migration 0041). The priority-30 `embedded` `MetadataProvider` (below NFO=100 / sidecar=50, above filename=10) maps them into the resolver merge → `Overview` / `OfficialRating` / `Studios` / `PremiereDate` (+ `ProductionYear` from `year`), so a user's curated NFO still wins every scalar but a sidecar-less file is no longer blank. A purely-numeric `content_rating` (an iTunes explicit-lyrics flag / star count) is dropped, not shown as a certification; a year-only `release_date` leaves `PremiereDate` unset. `PROBE_SCHEMA_VERSION` 4 re-probes existing rows so they backfill (B90/T100).
- V45: Every 200 image response (`/Items/{id}/Images/*`, indexed, chapter, and local-sidecar paths) carries a `Cache-Control: private, max-age=…` and a content `ETag` (file length+mtime), and a request whose `If-None-Match` matches the current ETag gets a bodyless `304 Not Modified`. All read paths funnel through one `deliver_image` helper so no image route can ship uncached. Rationale: before this, image responses set NO cache headers, so a gallery client re-downloaded every poster on every grid render / navigation — the posters-load-slowly complaint. 404 / person-redirect (302) responses stay uncached so newly-added art or a corrected redirect is not pinned (B89).
- V44: A video item's `Chapters` array carries a non-null `ImageTag` on every entry so a client renders the chapter thumbnail and fetches `/Items/{id}/Images/Chapter/{index}`; audio items (no extractable video frame) carry `ImageTag=null`. `image_tag_for(id, "chapter:{idx}")` mints the stable per-index tag; the `/Images/Chapter/{index}` route serves by index (ignoring the tag value) and extracts the frame on demand at the chapter's `start_ms`. A null/absent ImageTag makes chapters invisible — the client neither shows a thumbnail nor ever requests the image the handler is ready to serve (B88).
- V43: An episode list sorted by `SortBy=ParentIndexNumber,IndexNumber` comes back in air order (season then episode), never title order. The Jellyfin `ParentIndexNumber`/`IndexNumber` sort tokens are TYPE-OVERLOADED — season+episode for an Episode, disc+track for an Audio track — so `build_media_query` maps `SortPrimary::TrackOrder` to `(SeasonNumber, IndexNumber, Name)` when the query is episode-scoped (`kinds` contains `Episode`, OR the parent is a `Series`/`Season` pivot) and to `(DiscNumber, TrackNumber, Name)` otherwise. Mapping episodes onto the audio disc/track columns (NULL for episodes) collapsed every episode to the Name/Id tiebreak → an alphabetical-by-title list (Buffy S02E20 shown as the immediate next of S02E04) (B87). `SortKey::SeasonNumber` (`season_number`) is the new allowlisted column.
- V48: A DirectPlay/DirectStream `/videos/{id}/stream[.ext]` HEAD response reports the source's REAL byte length as `Content-Length` plus `Accept-Ranges: bytes`. A non-faststart mp4 (moov seek-index atom at EOF — most library files) is seekable only if the browser can learn the length to range-fetch the trailing moov; a zero/absent length collapses `seekable`→`buffered` (seek capped to already-buffered bytes). The HEAD is served via `actix_files::NamedFile` (body = `SizedStream`, `BodySize::Sized(len)`), NEVER a hand-built empty-body response carrying a manually-inserted `Content-Length`: actix's h1 encoder derives a HEAD's Content-Length from the body `BodySize` and DROPS the header, so an empty `()` body advertises `Content-Length: 0`. Sibling of V47 (the Range→206 half of Firefox seekability). Guard: jellyfin_stream.rs head_reports_real_content_length (B101).
- V49: Every live audio remux/downmix delivery (`/Audio/{id}/universal` → `audio_remux`) honours `StartTimeTicks` as an INPUT seek (`-ss` BEFORE `-i`). The output is a chunked ffmpeg pipe (no Content-Length, not byte-seekable), so jellyfin-web seeks by re-requesting with a fresh StartTimeTicks; ignoring it restarts the encode at t=0 and caps seeking to already-streamed audio. The ffmpeg argv is built by the pure `audio_remux_args` helper so the `-ss`-before-`-i` ordering is unit-asserted without spawning ffmpeg. Guard: stream.rs audio_remux_args_seek_is_input_option / audio_remux_args_no_seek_at_zero (B102).
- V50: Every HLS VOD playlist — video variant AND continuous-audio rendition — enumerates the FULL source timeline; its segment count derives from a duration resolved through `load_hls_item` (persisted probe → live-ffprobe fallback), never a `duration_ms.unwrap_or(0.0)` that a probe-missing row collapses to a single `.max(1)` 6 s segment (which caps seeking to the first segment). Guard: vp9_audio_rendition.rs audio_playlist_recovers_duration_when_probe_lacks_it (B103).
- V51: A library scan's mark-and-sweep of unseen rows is blast-radius-capped — it can never erase the catalog from a partial/failed source listing. `sweep_exceeds_guard(unseen, total)` BLOCKS (logs, no delete) a sweep that would remove BOTH >25% of rows AND ≥100 rows; a genuine large delete under the fraction cap still proceeds. A transient NFS mount that lists too few files while reporting `walk_errors==0` therefore cannot wipe the library (B98: 8192/13972 rows swept, Supergirl vanished). Recovery = fresh full mount + full scan (re-adds ungated). Guard: sqlite_store sweep_guard_blocks_catastrophic_mass_delete + sweep_guard_allows_large_delete_under_the_fraction_cap + small/large/fraction unit tests.
- V52: At most ONE library scan runs at a time; concurrent `/Library/Refresh` requests coalesce into a SINGLE pending re-run (force OR'd) that fires when the current scan finishes. `start_or_mark_pending` acquires the single slot or folds the request into the pending re-run; `finish_or_rerun` keeps the task Running across the re-run so there is no Idle gap a concurrent start could exploit; a cancelled pass never re-runs; the coalesced re-run rescans the full current media-root set. Prevents N concurrent full NFS catalog walks I/O-starving the node (B100: ~10 stacked scans → apiserver ServiceUnavailable). Guard: scan_tasks concurrent_starts_coalesce_into_one_pending_rerun + a_lone_run_with_no_pending_finishes_to_idle + a_cancelled_pass_does_not_rerun_even_with_pending.
- V53: Subtitle delivery is decided from the CLIENT's declared `DeviceProfile.SubtitleProfiles`, never a fixed text→External/image→Encode rule. A text/ASS format the client cannot render externally (absent from its SubtitleProfiles, or declared with a non-external method — e.g. the Jellyfin Android app, which omits ass/ssa by default) is BURNED into the transcode (`DeliveryMethod:"Encode"`, no DeliveryUrl, `SupportsExternalStream:false`); a client that lists the format External (jellyfin-web + SubtitlesOctopus) still gets the raw `Stream.ass`. When the selected (or default-disposition) subtitle must burn and the video decision is DirectPlay/DirectStream, `playback_info` downgrades it to Transcode so a burn always has a video stream (extends B80/V40 to the subtitle-selection path). The burn rasterizes text via the ffmpeg `subtitles=` filter reading the pre-extracted disk-cached `.ass` sidecar + a `fontsdir` of pre-extracted embedded fonts (NEVER the whole source per segment — that re-demuxes the NFS file + re-extracts fonts every 6 s, the documented stutter class), timestamp-aligned per segment via `setpts=PTS+start/TB, subtitles, setpts=PTS-start/TB` (the sidecar keeps absolute event times; `-copyts` is wrong — it collapses `-t`). Image (PGS/VOBSUB) burn stays on the `overlay` filter. Guards: subtitle_delivery unit tests, jellyfin_playbackinfo_subtitle_burn (Android burns / web stays External / DirectPlay downgrade / explicit-off stays DirectPlay), subtitle_burn_ass.rs behavioral (cue rasterizes at the correct absolute segment, from a standalone sidecar).
- V54: On the VP9/fMP4 path the separate continuous-audio rendition anchors its seek to the SAME frame-snapped grid the video segments use — `audio_seg_start_secs(seg, fps)` mirrors `segment_start_secs = round(seg*6.0*fps)/fps` — for BOTH the `-ss` input seek and the `-output_ts_offset`, and its playlist EXTINF is frame-aligned via `segment_time_range` like the video variant. Anchoring audio to the nominal `seg*6.0` while video sits on the frame-snapped grid leaves a fixed sub-frame A/V skew injected at every mid-file audio-track switch on a non-integer-fps source (B105). Any change to the audio seek anchor bytes bumps `HLS_GEN_VERSION` to orphan stale `_audiohls` dirs. Guard: hls_cache.rs audio_hls_args_seek_anchor_is_frame_snapped_to_video_grid (seg1 @ 23.976 fps → `-ss 6.006` + `-output_ts_offset 6.006`, never 6.000).
- V55: A mid-file audio-track switch seeks the audio rendition straight to the playhead, never re-encoding 0→playhead first. The rendition is one continuous ffmpeg run to EOF (no `-t`, `-hls_list_size 0`), so `want_seg` only governs WHEN a segment appears; the pure `choose_audio_start_seg(want_seg, from0_active, seek_progress)` reserves the whole-file from-0 session for a genuine start-of-file request, reuses a running from-0 session only within the near-start lookahead window, reuses a running seek session within its lookahead, and otherwise starts AT `want_seg`. - V58: Speculative transcode work NEVER takes capacity a client request needs, and NEVER queues. Every segment mint carries a `JobClass` (`Interactive` = a client response is blocked on it; `Background` = prefetch / prewarm), and the scheduler admits a `Background` job only while more than `background_headroom` (default 1) permits are free across the devices that could take it — otherwise it is shed immediately with `SchedError::Busy`, never pushed onto `pending`. Queuing speculative work is self-defeating twice: by the time a permit frees the client has usually requested that segment itself, and the queued job holds the segment cache's per-key fetch lock throughout, so the client request inherits the whole wait the prefetch existed to spare it. Shedding is reported as itself, not as breakage — distinct `HlsCacheError::SchedulerBusy`, DEBUG log, `pharos_segment_produced_total{outcome="shed",reason="scheduler_busy"}` — because deliberate load-shedding logged at ERROR drowns the real failures beside it, and logged nowhere is indistinguishable from silence. Guards: scheduler.rs speculative_work_is_shed_and_never_queues_in_front_of_a_client, _runs_when_there_is_spare_capacity, _leaves_headroom_for_a_client.

- V59: libav's own diagnostics NEVER reach a process's stderr. libav logs through a pharos-installed `av_log` callback (`libav::logbridge`) that renders each line onto the `tracing` target `libav` — fatal and above at ERROR, everything else at DEBUG — so the ordinary `EnvFilter` governs them and the default `info` prints none. Guards: logbridge.rs level_labels_are_distinct_and_stable, component_is_split_off_and_the_pointer_dropped, unrecognised_shapes_do_not_widen_the_label_set, installed_callback_receives_libav_messages.

- V60: A segment's window (`-ss` + `-t`) is derived ONLY from the segment index and the source frame rate — `pharos_core::SegmentWindow`, whose fields are private so no delivery path can state a position of its own — and it is clamped by the remaining media ONLY when that media's duration is actually KNOWN. `SegmentWindow::for_segment` takes `Option<f64>`, not `f64`, so an unprobed source cannot be spelled `0.0`: the grid floors its remaining media at 0.01 s, and clamping against a zero returns a 10 ms window for EVERY index rather than just the tail. - V61: A transcoded segment carries the tracks its rung declares and NOTHING else. `-sn` suppresses muxed subtitles and `-map_chapters -1` suppresses the source's chapters — the latter is a SEPARATE axis because chapters are not an input stream, so `-sn` never covered them and the mp4 muxer materialises them as a QuickTime chapter track (`codec_tag=text`, `handler_name=SubtitleHandler`, which ffprobe reports as a `bin_data` DATA stream) in the init `moov` of every fMP4 rung. - V62: Every transcode job records WHERE it was placed and HOW it decoded, at INFO — the level the deployment runs at. `record_placement` emits `transcode dispatch` with the winning device, the job class, the losing candidates and the excluded set (a CPU-only box and one whose GPU is in cooldown are indistinguishable without the losers), plus `decode_accel`/`decode_on_gpu` derived from `pharos_transcode::DecodeAccel` — the SAME value the argv builder emits `-hwaccel` from, so the reported figure cannot drift from what ffmpeg was told. - V63: A segment's cache key names only what changes its BYTES. `SegmentIdentity::new` folds the client's audio track into the key ONLY when the segment carries audio (`opts.audio_codec().is_some()`); the fMP4 rungs deliver audio as a separate rendition and end their argv in `-an`, so their output is identical across tracks and must land on ONE key. Guards: `an_audio_free_segment_is_not_keyed_by_the_audio_track` (same key, filename AND etag) and its converse `a_muxed_segment_is_still_keyed_by_the_audio_track`, which fails if the collapse is applied blanket and one track's bytes are served under another's request.

- V64: A wait on a producing session distinguishes SLOW from DEAD, and says which. `audio_hls_file_budget`'s stall budget is an inter-segment interval, not a latency budget — a continuous audio session emits one segment at a time, so the budget must exceed `SEGMENT_SECONDS` with margin or ordinary I/O contention reads as a wedge (asserted by `the_stall_budget_outlasts_a_realtime_audio_session`, not left as a hand-tuned number). Progress is read from the sessions that could actually SERVE the request (starts `<= want`, mirroring `resolve_audio_file`), and reports "not started" while the deepest of them has written nothing — a global high-water mark denied a freshly-spawned seek session the cold-start grace that existed for exactly its window (`a_fresh_seek_session_still_gets_the_cold_start_grace`). Corollary, same discipline: `out_bytes` is recorded only when the sink can measure it — a live-stream job's bytes go down the pipe, and reporting the unmeasured count as `0` made a healthy encode indistinguishable from a silent empty one (`only_a_file_sink_claims_to_have_measured_its_output`).

- V65: A SyncPlay member with NO SOCKET is awaiting a reconnect, not haunting the group, and is judged on `DISCONNECTED_TTL_MS` (10 min) rather than the ghost `MEMBER_TTL_MS` (150 s). The two describe opposite situations: a member silent WITH a live socket is a dead client holding a place in every readiness gate and must go promptly; a member whose socket is gone already holds nothing (`follower_ids` filters on `connected`), so an early prune achieves only the destruction of a membership its client is mid-reconnect to. A member hydrated by `apply_persist` is therefore restored `connected: false` — this replica has never seen its socket — which is both truthful and what makes the longer grace safe. Guards: `a_disconnected_member_survives_long_enough_to_reconnect` (survives past the ghost TTL, healed by a late `ResyncMember`) and `a_disconnected_member_that_never_returns_is_still_pruned` (the grace is a grace, not an amnesty).

- V66: Route registration order IS the routing decision between patterns of the same arity. Actix takes the first registered pattern that matches; a literal segment does NOT outrank a parameter. So `/items/{id}/images/chapter/{image_index}` must be registered BEFORE `/items/{id}/images/{image_type}/{image_index}`, or every chapter request is swallowed by the generic handler and answered `400 unknown image type` from a route the request never reached. Guard: `jellyfin_chapter_image_route.rs` drives the REGISTERED app (a shadowed route is invisible to a test that calls its handler directly) and distinguishes the two answers — 404 "chapter index out of range" proves the request arrived, 400 proves it was shadowed — plus a converse test that the generic indexed route still dispatches and still rejects a genuinely unknown type.

- V67: A produced segment is measured against the frames its window IMPLIES, not merely against a fraction of its duration. `SegmentWindow` keeps the `FrameRate` it was snapped to, so `expected_frames()` can count the frames presented in `[start, end)` — with `ceil`, not `round`, because the bounds carry the half-frame seek bias and both ends land on exactly `n + 0.5` frames, where `round` would decide a frame's ownership on the last bit of a float. Segments legitimately alternate 143/144 frames at 24000/1001 (the grid is a 6.000 s nominal snapped to frames, not a 6.006 s stride), so the asserted invariant is that adjacent windows TILE and account for every frame exactly once, not that each holds the same count; abutment is compared in TICKS, since a window stores its bounds at 100 ns resolution and consecutive segments may differ by that last unit. An unknown source rate yields `None`, never a guess, so an unprobed source cannot manufacture a phantom deficit. Every cache miss reports `expected_frames`/`produced_frames`/`frame_deficit`/`produced_secs` and counts `pharos_segment_frames_total{result}`; a shortfall warns. This exists because the pre-existing completeness check could only see a segment that missed 10% of its duration — 600 ms at 6 s, ~14 frames — so a stutter-scale shortfall passed as healthy, was cached, and replayed on every later view. Guards: `a_window_knows_how_many_frames_it_implies`, `a_window_with_no_known_rate_implies_no_frame_count`, `a_segment_missing_frames_is_measurable_even_though_the_gross_check_passes`.

- V68: A segment's audio source is settled BEFORE it can be lowered, and the type says so. `SegmentOpts` is the request and carries no audio-source field; `ResolvedAudio` is the settled answer, whose `Muxed(codec, slice)` variant cannot be constructed without the slice; `ResolvedSegment` is the only thing with a `to_transcode_options`. `SegmentOpts::resolve`/`resolve_with` are the only constructors and run the caller's closure for exactly the deliveries needing a slice, so it cannot be skipped, forgotten, or passed as `None`. Applying this found a SECOND instance the runtime fix had missed (the uncached live fallbacks in `hls_segment` and the VP9 path, which have no cache to produce a continuous encode and now say so with the reason) and a test asserting a contradiction (`segment_frame_completeness` declared `Muxed` with no source, so it had been encoding video-only all along). - V69: Where a client dialect has two legal spellings of one request, pharos serves BOTH. Chapter thumbnails are addressed `/Images/chapter/{n}` by jellyfin-web and `/Images/chapter?imageIndex={n}` by jellyfin-sdk-kotlin (Android / Google TV); serving only one 400s an entire client's chapter strip. - V70: A per-segment video encode is pinned to the SOURCE frame grid on EVERY device. The software encoders take `-enc_time_base 1:90000`; the hardware encoders reject it and take `-r <source rate>` instead, which `SegmentWindow` makes possible by keeping the `FrameRate` it snapped to and lowering into `TranscodeOptions::source_frame_rate`. Without one of the two an encoder quantizes the zero-based first-frame pts to its default 1/framerate timebase, places the first frame half a frame late and loses the last — exactly one frame per segment. `-fps_mode passthrough` is NOT a substitute: it restores the frame count while still leaving a one-frame gap at the join, i.e. it fixes the number and not the tiling. `-r` is emitted only when the rate is genuinely known, because a guessed rate resamples the picture. Guards: `a_hardware_segment_encode_is_pinned_to_the_source_frame_grid` (hardware gets `-r 24000/1001` and no `-enc_time_base`; software keeps `-enc_time_base` and gets no `-r`) and `an_unknown_frame_rate_pins_nothing`.

- V71: `MuxedAudio::start_seconds` is where the FILE actually starts, never where its session was asked to start. A segment slices the continuous encode with `-ss (input_seek - start_seconds)`, and `-ss` on an input is measured from THAT INPUT'S OWN START TIME, so any error in the field shifts the audio under the video by exactly that much. The two coincide only for sources whose audio stream begins at 0: a from-0 session on a source whose audio starts late produces a file whose first sample is at the stream's own start (ffmpeg preserves it — verified by running the production argv against the real file), while the session records `0.0`. `ensure_continuous_audio_covering` therefore PROBES the produced file's first audio packet and records that, cached per session file, falling back to the requested start when the file cannot be probed yet. A session that does not start where it was asked to logs the skew at INFO. Guard: `the_slice_seek_honours_the_files_true_start_not_its_requested_one` asserts BOTH directions — true start puts the tone under the right video, `0.0` shifts it a whole segment early — with a short tone placed just past a segment boundary, because a wide tone cannot separate the cases (the first version of that test used a 2 s tone against 6 s segments and passed against the bug).
- V72: the demuxed audio rendition must sit on the SOURCE timeline, in content and in anchor, and neither half can be assumed from the other. Content: ffmpeg re-bases the only mapped stream so its first sample sits at zero, discarding an audio track's own start time, so the whole-file session is padded by that start (`-af adelay`) — measured on ffmpeg 8.1, `-output_ts_offset`, `-copyts` and `-avoid_negative_ts disabled` all leave the content where it was, and a SEEK session needs no pad because `-ss X` lands on source X exactly. Anchor: ffmpeg's HLS muxer numbers each session's `tfdt` from that session's own first fragment whatever it is passed, so a fragment is shifted by its producing session's start when served, which is the only place that start is known. Guards: `a_late_starting_audio_track_still_lands_under_its_own_video` DECODES a fragment and locates a known beep (a header assertion cannot see a content shift, and asking for the segment directly spawns a seek session that lands honestly and would test nothing — the test must request segment 0 to exercise the whole-file session); `shifting_moves_every_tfdt_by_the_same_delta` and `a_seek_sessions_fragment_reports_the_session_it_came_from` pin the anchor.
- V73: the tracks a client is told to start on are the user's, not the container's. Order: an explicit pick on THIS request; then the track that user last played this item with (`RememberAudioSelections` / `RememberSubtitleSelections`, including a remembered `-1` = subtitles off); then Jellyfin's selector over the user's `AudioLanguagePreference` / `PlayDefaultAudioTrack` / `SubtitleMode` / `SubtitleLanguagePreference`. The selector is a faithful port of `Emby.Server.Implementations.Library.MediaStreamSelector` — including the trap that a container's default-flagged track BEATS the language preference while `PlayDefaultAudioTrack` is on (Jellyfin's default), which is why Aliens keeps playing Ukrainian until that setting is turned off. Faithful because the settings are configured from stock jellyfin-web: pharos must do what that UI describes, so upstream's own score table and audio-selection vectors are asserted digit for digit. `OriginalLanguage` ranks by the title's own `original_language` (recorded by enrichment from TMDB), degrading to no preference — never to a guessed language — for an item nothing has enriched. A progress report that does not name tracks never erases a remembered choice: both the write path and the UPSERT `COALESCE` onto the stored value.
- V74: a landscape image is chosen art before it is an extracted frame, and the picker offers only what can be stored. Neither online provider publishes a thumb image type — TMDB's `/images` carries `posters` / `backdrops` / `logos`, TVDB the same — so a Thumb has exactly three sources, in order: the item's own Thumb row (a `landscape.jpg` sidecar or an episode still), then its Backdrop, and only then a frame extracted at `image_seek_seconds`. The frame is last because nobody chose it: on a film with a dark opening it is the title card. `pharos_image_thumb_source_total{source="artwork"|"backdrop"|"frame"}` counts which answered, so the items still falling to a frame are countable rather than merely visible. The same substitution runs in the online picker — a `Type=Thumb` search offers the backdrops — but ONLY for a real `media_items` row: `series_metadata` records a poster locator and a backdrop locator and nothing else, so a container's Thumb pick could not be persisted and is refused rather than half-applied.
- V75: a detector's silence must be explainable. Intro/outro detection finding nothing is the COMMON case — most shows have no shared intro — so a season that emits nothing is indistinguishable from one whose segments were found and discarded unless the gate's inputs are recorded: `detect_season_verbose` keeps every episode's `matched` / `agreeing` / `confidence` and the `Verdict` that rejected it, `detect_season` is a filter over that, and the backfill logs the per-season counts plus each dropped episode's own numbers and counts them as `pharos_segment_detect_total{kind,outcome}` from a `label()` method. Agreement is scored against the comparisons that LOCATED a span, never against every peer in the season: a peer that aligned nothing offered no evidence, and dividing by it made recall fall as a season grew longer. And the analysis is stamped separately from its result (`media_segment_scans`), because an empty detection writes no segment row — conflating the two re-analysed every intro-less season on every pass forever AND left a version bump unable to reach an episode with no row to carry a version. The fingerprint version and the detection version are distinct: a consensus change must re-run pairwise comparison over cached points, not re-decode the library.
- V76: an `ImageTag` is a VERSION, not an identity. The tag is what a client compares to decide whether to re-fetch, and images are served `Cache-Control: private, max-age=604800`, so a tag derived only from (item id, role) pins a browser to whatever it cached for a week — a picked, uploaded or deleted image overwrites the item's deterministic cache slot and produces the same URL, which is never revalidated. The premise that made that safe (an image is a deterministic re-extraction, so its identity IS its version) stopped being true the moment art could be REPLACED. `media_items.art_version` is therefore an input to `image_tag_for` alongside the item and the role, and every path that replaces bytes under an existing slot bumps it: the RemoteImages download, the manual upload, the delete. `set_artwork` deliberately does not — the scanner re-records identical sidecar paths on every pass, and a tag that rotates when nothing changed is a cache-buster, not a version. The ETag is not a substitute: it was correct and did change throughout, and was never consulted, because a client that believes its copy is fresh sends no request to attach it to.
- V77: a poster is asked for by the role the CLIENT requests, and a provider is asked until one of them answers. An episode's still is its `Primary` — Jellyfin's episode tiles request Primary and nothing requests an episode Thumb — so filing a still under Thumb enriches an episode into a state where it still advertises no poster and falls to a frame. A show's `/series/{id}/extended` body carries `artworks[]` alongside `data.image`, so the backdrop and logo come from the response already in hand, chosen by best community score, rather than being left absent. And no single provider is authoritative: TVDB declining a title is not evidence the title is unmatchable, so TMDB is tried after it — with a provider ERROR kept distinct from a genuine no-match, because collapsing the two writes `none` and freezes the show for the refresh TTL on the strength of a blip. Beneath all three the frame extract remains, and it is the LAST resort by construction: nobody chose it, so anything that reaches it is a gap to be counted, not a result.
- V78: a rendition's segments and its init share ONE clock, and that clock is a property of the output format — never of the device that happened to be free. Every fMP4 segment is muxed on `FMP4_TRACK_TIMESCALE` (90000, the MPEG clock the mpegts segments already use), pinned at the muxer with `-video_track_timescale`, because the encoder-side frame-grid routes legitimately differ per device (`-enc_time_base 1:90000` for software, `-r <source rate>` for hardware — V70) and the muxer would otherwise inherit whichever ran. A segment on a different timescale is not rejected by anything downstream: the player divides it by the init's timescale regardless and lands the whole fragment at `actual/expected` times its true position. So each produced segment is judged against the pin and counted as `pharos_segment_timescale_total{verdict}` from a `label()` method, with the offending timescale in the log line rather than a bare class, and the init route is judged too — an init on the wrong clock mis-reads every segment that follows it. Frame completeness (V67) cannot stand in for this: it passed on every affected segment, because the encoder produced exactly the frames asked for.
- V79: a title-match score treats an appended tail as evidence RETAINED, not evidence against. `title_similarity` scored a local name against a provider's canonical title as pure length-normalized Levenshtein, so a provider that appends a subtitle (`Code Geass` vs `Code Geass: Lelouch of the Rebellion`) or a local name that adds a qualifier (`Forever (US)` vs `Forever`) drove the edit distance up in proportion to the length GAP and sank the score below the `match_min_confidence` floor (0.7) — recording the show `none` with no poster, no backdrop and no episode stills, exactly the shows V77's TMDB fallback was meant to rescue and could not, because the fallback still runs the same scorer. When the shorter normalized title is an exact whole-token PREFIX of the longer, the shared portion is a perfect match and only the dropped tail is uncertain, so `prefix_containment` scores it `0.9 + 0.1·(coverage)` and `title_similarity` returns the max of that and the Levenshtein. A minimum shared-prefix length (`MIN_PREFIX_MATCH_CHARS`) keeps a trivial leading word (`Code`, `24`) from blanket-matching an unrelated show — below it the whole-string Levenshtein still governs. The prefix must end on a token boundary (`forever` matches `forever us`, never `forevermore`), and the relation is symmetric so it fires whichever side carries the tail. Distinct from a genuinely unmatchable on-disk name: a season folder promoted to a series (`Season One`) or a raw release filename is a SCAN defect, not a scorer defect, and is out of this invariant's scope.
- V80: every segment of a shared-init fMP4 (CMAF) rendition must come from ONE encoder, because they all decode under a single init whose codec-private data is seg0's — and a parameter set, unlike a mux parameter, cannot be forced identical across two encoders. A CMAF media segment carries no inband SPS/PPS; the client configures its decoder from the init's `avcC` (seg0's SPS) and reads every later segment's slice headers against it. The scheduler load-balances each segment across NVENC and CPU by design (fine for the self-describing mpegts rungs, which repeat parameter sets per segment), so an h264 CMAF session could split across `h264_nvenc` and `libx264` — whose SPS differ in the slice-header determinants (POC type, `log2_max_frame_num`, ref structure) that `-profile`/`-level`/`-refs` do NOT cover — and a spilled segment is then decoded with the wrong SPS: `avcodec_send_packet: Invalid data`, the browser stalls. This is the parameter-set sibling of V78's timescale (which WAS a mux param and could be pinned). `device_supports` therefore makes hardware ineligible for `H264 + Container::Fmp4`, pinning the whole CMAF rendition — init and every segment — to libx264 (realtime at `-preset veryfast`, self-consistent, and it frees the GPU). Scoped to Fmp4: the mpegts h264 variants keep hardware. Frame completeness (V67) and the timescale pin (V78) both pass on a segment whose SPS is wrong — neither reads the parameter set — so this is its own gate, verified by decoding a spilled segment under the rendition's init.
- V81: the track the server SELECTS must ride the delivery URL, not only the DTO. V73 chooses the audio track a user starts on and reports it as `DefaultAudioStreamIndex`, so the UI shows it selected — but the demuxed audio rendition is a separate HLS session keyed by the `AudioStreamIndex` on its request, and that index reaches it only through the `TranscodingUrl` the server hands back. `stream_selection` forwarded only an index the CLIENT named on the request, and on first play jellyfin-web names none (it trusts the server's pick and appends `AudioStreamIndex` only after a manual switch), so `resolve_audio_rel` saw `None` and ffmpeg default-selected the container's first / default-disposition track: Aliens (three Ukrainian tracks ahead of its English DTS-HD MA) showed English selected yet played Ukrainian; Campfire (English default ahead of Japanese) showed Japanese yet played English. The selection was also computed AFTER the URL was built, so it structurally could not ride it. The server-selected absolute index (the one that becomes `DefaultAudioStreamIndex`) is therefore appended to the transcode URL when it carries none (`ensure_audio_index_param`, mirroring the `StartTimeTicks` append), idempotent with a client's later manual switch. A DTO field that says which track is selected is not the same as delivering it — the value that drives the render path must carry the choice too.
- V82: a capability field a client GATES a request on is answered from the same source that would serve the request. `MediaSource.HasSegments` is computed by `item_has_segments` from the detected segment rows plus the classifiable chapters — exactly what `/MediaSegments/{id}` returns — so the advertisement cannot promise what the endpoint lacks, nor hide what it holds. A hardcoded `false` on such a field is not a harmless stub: jellyfin-web returns before it ever calls `getItemSegments`, so the feature is unreachable with no failing request to find (B130). The verdict is recorded, because `false` is a decision and the field alone cannot distinguish "nothing to skip" from "never looked".

- V83: a search's DISCOVERY step and its ACCEPTANCE step use the same notion of similarity. Fingerprint alignment accepts two points at a Hamming distance of `max_bit_diff`, so its candidate shifts are enumerated over the overlap rather than seeded from exact-value equality — a pair of episodes sharing an entire opening within the acceptance tolerance must never fail for want of a numerically adjacent point (B131). Guards: a synthetic block whose points are all inside the bit tolerance and all outside any exact-value probe must still align, and the real-fingerprint fixture must locate the opening wherever it is present. Filler in a detector test is AVALANCHED, never stepped: an arithmetic ramp differs by a constant at every index and so aligns with itself under some shift, modelling an agreement real fingerprints cannot produce.


- V84: background work is throttled where its COST is, not where its cost used to be. `bg_io` regulates background *I/O*, and season consensus was left outside it because it had been cheap arithmetic over an indexed shift set. B131's exhaustive search moved the cost to CPU without moving the gate, and the work also ran inline on a tokio worker — so it could neither be parked by the regulator nor kept off the executor serving playback. Any background stage that becomes long-running holds a `bg_io` permit for its duration AND runs on `spawn_blocking`; a stage that does neither is invisible to the "stand down during playback" contract no matter what the adjacent stage does.

- V85: a consensus gate weighs evidence by its MAGNITUDE, not by its count. Season detection scored agreement as `agreeing / matched`, so three peers agreeing on a 109 s title sequence (0.43) lost to four short coincidental fragments, and every Game of Thrones S1 episode was discarded at 0.38-0.43 while adjacent seasons emitted the same span at 0.63-0.88. Counting votes treats an 18 s fragment and a full opening as equal testimony. Weight by matched seconds (T102); keep a separate `min_agreeing` count so one long coincidence still cannot carry an episode alone.

- V86: a derivation that REPLACES its own prior output snapshots it first, under a label, idempotently. `media_segments` is rewritten in place by a detector re-run, so the moment the sweep starts the evidence needed to judge it is gone — when SEGMENT_DETECT_VERSION 2->3 ran, "did recall drop?" was asked minutes later and was unanswerable. The snapshot must be taken before the first replacement and must never overwrite itself on a later pass, or it captures the post-change state and answers nothing (T103).

- V87: a search that rejects a candidate keeps looking among the rest. `compare` took only the LONGEST contiguous run at a shift and handed it to `bound_and_snap`; a run failing the duration bounds killed the entire shift, even when a shorter valid run sat at that same shift. Enumerate runs and take the first that clears the bounds on both sides (T104) — "best candidate" and "only candidate" are not the same thing.

- V88: when two readings of the same evidence fail in OPPOSITE directions, requiring both is a recall bug — take the better one and floor it separately. Season agreement was `agreeing/matched` (T102 showed a long true opening outnumbered by short coincidences: Game of Thrones S1 dropped entirely at 0.38-0.43), then `agreed_secs/located_secs` (T107 showed a short true ending outweighed by long spurious matches: Breaking Bad S5 credits 6 emitted -> 0, 78 outro rows lost library-wide). Each ratio is evidence, neither is the definition. The gate now clears on the greater of the two with `min_agreeing` as the independent floor. Corollary: a threshold change is not validated by the cases it was designed to fix — diff BOTH kinds against a pre-change snapshot (V86) before believing it.

- V89: when the RULE that assigns work to a device changes, every artefact cached under the old rule is stale — even if the artefact itself is still valid. Spec 003 moved CMAF H264 from "always CPU" to a deterministic device resolving to hardware, and research R8 argued no cache-generation bump was needed because a deterministic device means cached bytes always came from the device the rendition still resolves to. That holds only while the rule is FIXED; the deploy that introduces the rule is itself the moment it changes. Live consequence: 1489 CPU-era cache hits served alongside 11 fresh NVENC encodes for one episode, i.e. a libx264 init with hardware segments under it — the B-class #114 pairing failure, from disk rather than from the load balancer. Bump the generation whenever the assignment rule changes, not only when the device table does.

- V90: a response served `immutable` must have its identity IN THE URL. Anything the bytes depend on that is not in the URL becomes unfixable from the server: the stale copy lives in the client. `init.mp4` and `.m4s` are served `max-age=31536000, immutable` under URLs naming only item + segment index, so when the encoder assigned to CMAF changed, browsers paired an old init with new segments (B133/#114) and neither a server cache wipe nor a playback restart could clear it. Shared-init rendition URIs therefore carry `HLS_GEN_VERSION`. Corollary for diagnosis: when a fault survives a server-side cache invalidation, suspect the CLIENT cache before concluding the newly produced bytes are malformed — that inference cost a revert of a working feature.

- V91: whatever the miss path records, the hit path records too — a cache is not exempt from symmetry (V-class sibling of the rich-on-success/silent-on-failure shape). `segment_bytes_keyed` logged twelve fields on a miss (`transcode_ms`, `device`, `queue_wait_ms`, `frame_deficit`, …) and, on a hit, incremented one bare counter on its FAST branch and recorded NOTHING AT ALL on its post-lock re-check branch — so a segment served after queueing behind a concurrent mint of the same key appeared in neither the hit rate nor the miss rate. The consequence is not a missing nicety: the 2026-07-28 "Disclosure Day" investigation held 647 segment requests against 490 logged transcodes and could not say which of the remainder were cache hits, nor what had produced those bytes, so "was this session served stale output?" was unanswerable from the record. Both hit branches therefore emit `pharos_segment_cache_total{result,class,hit_path}` and an `hls segment served (cache hit)` line carrying the same identity fields as the miss line (`codec`, `burn`, `audio_idx`, `seek_secs`) plus `age_secs` and `read_ms`. `hit_path` is bounded to `fast` / `post_lock` and appears as `none` on a miss, because a label present on only one arm of a ratio silently drops series. `age_secs` is the field that distinguishes a hit on this session's own prefetch from a hit on an entry old enough to predate a deploy — the V89/V90 question, which no signal could previously answer.

- V92: speculative work is aimed at the request that will actually be made, and says where it aimed. The cold-start prewarm warmed segments `0..3` unconditionally while playback began wherever the viewer had resumed, so on a resume it was worse than doing nothing: three background encodes spent on bytes no client would fetch, AND the cold ffmpeg spawn the prewarm exists to absorb left sitting on the first request the client actually made (B136). A speculative stage therefore derives its target from the same position the response advertises (`start_position_ticks` / `StartTimeTicks`) and resolves it through the SAME `SegmentGrid` the playlist enumerates — deriving the index independently is how a warm segment and a requested segment drift apart. It also records what it chose and why, because a prewarm aimed at the wrong end of a title is indistinguishable at the metrics from one aimed correctly: both simply produce segments. Corollary: when a speculative stage cannot determine its target (no duration, position past the end) it declines rather than falling back to a default, since the default is precisely the case it is trying to stop being wrong about.

- V93: a control-plane WAIT states who it is waiting on and how it ended. A gate that logs only `pending=1` cannot answer "why is nothing happening?", and a gate rescued by a timeout that logs the same line as one every member acked makes a hang indistinguishable from health — B137 froze a group watch for ~37 s and had to be reconstructed from four Loki queries and three hand-correlated streams because both were true at once. So: every readiness gate names its holdout member ids at open, carries a reason label finer than the jellyfin wire string it broadcasts (five distinct situations all send `"Unpause"`, and they have different diagnoses), and terminates in exactly ONE recorded outcome — `resolved`, `anti_wedge`, `superseded`, `replaced` — which therefore sum to the number of gates opened, so a path that drops a gate shows up as arithmetic drift rather than as silence. The same holds for the V19 buffering freeze, whose only client-visible act is a bare `Pause` byte-identical to a user pressing pause: it records `recovered` / `superseded` / `anti_wedge` and how long it held, because "the group recovered" is not evidence of health when a human seeking out of the freeze is what ended it. Corollary, and the sharper half: an input the server DELIBERATELY discards is still an event. B137's viewer pressed play twice into an open gate; both presses were dropped correctly (replacing the gate would reset the anti-wedge deadline) and recorded nowhere, so the server's account showed a frozen group with no sign anyone had tried to resume it. A discard is a decision, and decisions are instrumented (ODD principle 2) — otherwise the most common user report there is, "I pressed the button and nothing happened", is unanswerable by construction.

- V94: a response that stops short of what the client asked for is only valid for a client that will ask again. Truncating a range is not a neutral optimisation — it is a statement about the media's length to any player that sizes its read from `Content-Length`, and a native progressive player believes it. Before capping, narrowing or otherwise shortening a body below the requested extent, name the client shape that re-requests the remainder; if it cannot be named, serve the whole extent. B140 truncated every Android TV DirectPlay to the first 8 MiB with a browser-shaped fix and reported three healthy 2xx responses while doing it.

- V95: artwork that pharos has downloaded is artwork pharos advertises. The `artwork` table mixes on-disk locators with bare remote URLs, and exactly one predicate decides which is which — `pharos_core::artwork_source_is_item_servable`. It is consulted by the sqlite and postgres `set_artwork` writers, which maintain the denormalised `has_primary_art`, and by the image route that resolves a role to a path; a new artwork source added to some of those and not others caches bytes that are never advertised and never served, with no error anywhere. One list, one home, asserted in a test that names every provider which downloads bytes (T108).

- V96: an endpoint a stock client calls by name exists, even when its data is empty. jellyfin-web issues many fetches with no rejection handler, so a missing route is not an error the user sees — it is a view that never finishes loading, and the report names the screen rather than the request. Before concluding a library is empty or broken, list what the client actually asked for and check every path resolves; `{namespace="pharos"} |= "status\":404"` is the query. B141 (`/MusicGenres`), the Edit Images spinner (`/Items/{id}/Images`) and the stuck audio switch (`DELETE /Videos/ActiveEncodings`) are the same bug three times.

- V97: a cached negative result records the logic version that produced it. Any sweep that stamps "we looked and found nothing" and then honours a TTL is asserting that the answer cannot change — but it changes every time the lookup improves, and the improvement then appears to do nothing for the whole TTL on exactly the items it fixes. Stamp the version alongside the verdict and invalidate on mismatch, the same discipline `PROBE_SCHEMA_VERSION`, `TRICKPLAY_GEN_VERSION`, `HLS_GEN_VERSION` and `SEGMENT_DETECT_VERSION` already apply to cached positive results. B143 is the negative-result case of the same rule.

- V98: a field a strict client dereferences unconditionally is set in the constructor, not at the call site. The kotlin SDK's DTOs are non-null; the Android TV app reads `item.userData.isFavorite()` with no guard, so an omitted `UserData` is a crash rather than a blank. Fixing that per-endpoint is how B68 was closed for library folders while every synthesised item kept the same hole for another year. When a client-required field is discovered, set it in the shared constructor and assert it across every surface that constructor feeds — the assertion over ALL surfaces is what proves the fix is structural (B146).

- V99: a cached failure remembers WHY it failed. Memoising a miss as a bare absence makes every repeat report a stand-in cause, and since repeats vastly outnumber first attempts, the aggregate signal then describes a problem nobody has. B147 read 192 `no_candidates` against 26 `below_confidence` when nearly every miss was below-confidence, and the ratio pointed at the query for two rounds of fixes while the real fault was in scoring. Store the reason, not just the failure, wherever a per-item verdict is cached and counted.

- V100: relaxing a query removes a constraint, so the constraint has to be re-applied when the result is judged. Each rung of a search ladder that drops a term widens what can come back, and scoring that ignores the dropped term cannot tell the widened results apart — B150 dropped the artist from the query AND from the score, and 217 albums called `Fireflies` became indistinguishable perfect matches. Whatever a rung drops, the acceptance test must check. Corollary: a cached result is only as trustworthy as the matcher that produced it, so record the matcher's version alongside it and invalidate on a bump — a wrong answer that already looks answered is invisible to every later pass.

- V101: a filter that names something unknown narrows to nothing, never widens to everything. Parsing a client's filter into "the values we recognised" loses the difference between "no filter asked for" and "a filter we cannot satisfy", and defaulting the second to the first turns a precise request into a whole-library scan — B153 answered a request for music videos with 51.6 MB of films and episodes. Represent the empty-after-parse case explicitly and decide it deliberately; where a named value is one the server answers by synthesis rather than storage, say so in a list that can be read, not by accident of a parser returning nothing.
- V102: a group's poster comes from a member that HAS one. When an aggregate item (album, artist, series, library) picks a representative member to stand in for its image, membership in "has art" ranks ahead of every cosmetic ordering key. Ordering by title/number alone silently picks a blank member out of a group that is not blank, and the wire shape is indistinguishable from a group with no art at all (B154).
- V103: a cache whose correct answer depends on data a background job is still writing must be invalidated by that job, not by restart. Memoised derivations of mutable state (the synth-image representative map) carry an epoch the writer bumps; a reader that finds a moved epoch rebuilds. "It fixes itself on the next deploy" is the signature of this class (B155).
- V104: every id an endpoint HANDS OUT must resolve when handed back. A list builder that emits a synthesised id creates a client navigation target; the item-detail fetch has to resolve that id shape or the surface dead-ends. New synth id shape → a resolution arm in `fetch_item_dto`, in the same change (B156).
- V105: fetch the size you are going to render. When a provider publishes derived sizes, request the derivative that covers the largest surface that displays the asset — never the original. And a network client gets a connect timeout separate from its whole-request timeout, so "host is down" and "transfer is slow" stay distinguishable (B158).
- V106: a decision with several rejection grounds must report the one that actually fired, and the value it fired on. Reusing a neighbouring metric for the message produces reasons that contradict the verdict and send the reader to tune an uninvolved threshold — strictly worse than saying nothing. Corollary for the TEST: assert the SELECTION of the reason, not its formatting; a test that hand-builds the variant and checks its `Display` passes with the routing disarmed (B159).
- V107: invalidation is priced by what it destroys, so a cheap trigger must not fire an expensive one. Separate "re-examine what FAILED" (free — re-admit the rows that recorded a failure) from "discard what SUCCEEDED" (expensive — re-fetches everything from a rate-limited provider), and gate them on different versions; bump the destructive one only when a past success may be wrong. And an ABSENT version record is not a stale one — adopt it silently, or every fresh install pays a full rebuild on first boot (B160).
- V108: a payload that exists to be MEASURED must be incompressible, and must say so. Anything whose size is the point — throughput probes above all — has to resist every layer that might helpfully shrink it, both by construction (high-entropy content) and by declaration (`Content-Encoding: identity`). Filling such a body with a cheap constant makes the measurement a function of the compressor rather than the link (B161).
- V109: compress at the layer that only sees text. Response compression belongs where it can be scoped to text-shaped content types by an allow-list, not on a path that also carries media: a compressor that switches a video or image response to chunked transfer breaks the `Content-Length`/`Range` contract those paths depend on. Byte-exact payloads (throughput probes) stay outside the allow-list (B162).
