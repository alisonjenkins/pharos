# Invariants — pharos baseline

Normative register. Migrated verbatim from `SPEC.md` §V on 2026-07-27. These are
the non-negotiable properties every plan and change is checked against (see
`.specify/memory/constitution.md` → Governance). Numbering (V1…V81) is stable and
load-bearing — tasks, bugs and code comments cite these ids. Never renumber; append.

- V1: unmodified Jellyfin client connects, browses library, plays media (direct + transcoded).
- V2: unmodified Plex client connects, browses library, plays media (direct + transcoded).
- V3: group session syncs play/pause/seek across members within 500ms p95.
- V4: HTTP handler never panics. Errors return structured response matching target API schema.
- V5: library scan never blocks playback or API requests. Scan runs in dedicated task pool.
- V6: ffmpeg subprocess crash never crashes server. Failed transcode returns error to client.
- V7: API response shapes match Jellyfin/Plex reference schemas byte-equivalent for shared fields.
- V8: auth tokens never logged. Secrets redacted in all log output.
- V47: a response to a Range request that carries Content-Range is 206, never 200 (Firefox `<video>` `bytes=0-` open probe must confirm seekability).
- V9: media file path never leaks to unauthenticated client. Path traversal blocked at boundary.
- V10: store writes atomic per logical op. No partial library entry visible to readers.
- V11: every public behavior covered by test written before impl (TDD). No merge without failing-test-first evidence.
- V12: trait boundary between domain logic and IO. Domain layer testable without DB/fs/network/ffmpeg.
- V13: every inbound request traced. Every outbound IO (db, ffmpeg, fs walk, http client) spanned. trace_id propagated to logs.
- V14: `/healthz` returns 200 if process alive. `/readyz` returns 200 only when store reachable + scanner initialized. `/metrics` exposes Prometheus format.
- V15: structured logs only. No `println!`/`eprintln!` in non-test code. `tracing` crate sole logging surface. CLI subcommands may write to stdout/stderr via explicit `std::io::Write` (not logging).
- V16: Dioxus UI consumes only public Jellyfin-compat API. No backdoor endpoints. UI swappable for any Jellyfin client.
- V17: no `unwrap()` / `expect()` in non-test code. Enforced via `clippy::unwrap_used` + `clippy::expect_used` = deny at workspace level. Tests may opt-out.
- V18: mutable runtime state owned by exactly one task. Mutation via message-passing (tokio mpsc). No `Mutex<State>` on request path. Locks permitted only for one-shot init or immutable-after-init caches.
- V19: group-sync must improve on Jellyfin SyncPlay failure modes. Specifically: (a) late joiner does not desync existing members; (b) one poor-network member does not stall the group (per-member buffering isolation); (c) leader handoff causes ≤1 corrective Pause, no buffer storm; (d) network blip <2 s reconverges automatically without member rejoin.
- V20: group-sync wire protocol stays Jellyfin SyncPlay-compatible so unmodified phone/TV clients participate. Improvements live in server-side algorithm. A second WS path may carry an extended protocol for pharos-native clients, but the Jellyfin-shaped socket is the canonical entry point.
- V21: SyncPlay server never withholds command client must ACK. Readiness gate waits only on members expected to emit player transition (queue load, already-delivered Seek, active buffering). Plain Unpause of non-buffering group broadcasts immediately. Every SendCommand carries PositionTicks (jellyfin-web seeks to it — missing value = seek to 0). SetIgnoreWait honored: halted member excluded from all gates.
- V22: Quick Connect wire flow matches jellyfin-web two-endpoint exchange. `/QuickConnect/Connect` is read-only poll — echoes `Secret`, reports `Authenticated`, never mints token, never consumes. Finalize at `POST /Users/AuthenticateWithQuickConnect` {Secret} (unauth — secret IS credential): single-shot consume of an AUTHORIZED entry → AuthenticationResult (User + AccessToken). Unauthorized/unknown/spent secret → 401. Its query params (`secret`, `code`) bind case-INSENSITIVELY — mobile/TV SDKs send camelCase, jellyfin-web PascalCase; real Jellyfin (ASP.NET) is case-insensitive, so a case-sensitive extractor 400s non-web clients.
- V23: software video transcode jobs are thread-bounded + speed-preset. Every sw encode AND decode capped at `sw_encode_threads()` (≈4); libx264/libx265 get `-preset veryfast` (never x264 default `medium` — below realtime under load); CPU permit budget = `cores / sw_encode_threads()`, never permits=cores (double-counts: each job auto-threads all cores, all admitted jobs slow below realtime together); prefetch depth derives from permits, capped at 4. Invariant: `permits × threads-per-job ≤ cores`.
- V24: a synth group id (Series/Season/Artist/Album) serves LEVEL-specific art before any representative-member fallback. Seasons: probe the Kodi/Jellyfin series-root sidecars (`season{NN}-poster/-fanart/-banner`, zero-padded + bare, `season-specials-*` for S0) for the season the id names; only then fall back to the representative episode's artwork (series poster). Fallback must never make two different groups of one show serve identical bytes when level-specific art exists on disk.
- V33: the video transcode target codec PREFERS H.264 whenever the client advertises it (`negotiate` picks h264 out of the transcoding profile's `video_codec` CSV, not the first-listed). H.264 is the shareable target: the segment cache key is `(media, seg, audio, sub, bitrate, codec)` with no user/device, so every SyncPlay group member transcoding to h264 hits ONE cached encode. Honouring the client's first-listed codec split a group across encodes — a browser listing `vp9,h264` cold-transcoded its own (software, slow) VP9 while the rest shared a warm h264 stream, so it stalled and never joined shared playback. A client offering no h264 (VP9/AV1-only) still gets its first codec; the Linux-Firefox-can't-decode-h264 case is forced to VP9 downstream (`playback_info` `force_webm`), which overrides this. PlaybackInfo logs the full codec decision (`playbackinfo: codec decision` — is_firefox, client_offers_vp9, force_webm, negotiated codec, route).
- V32: a member's delivery sink in `MemberSinks` is GENERATION-FENCED — every insert/remove carries the owning socket's `conn_gen`. An insert lands only when its gen ≥ the stored gen; a remove fires only when its gen == the stored gen. So no stale writer (the losing task of two racing connects for one deterministic member_id, or an HTTP New/Join re-registering a sink snapshot resolved just before a reconnect) can ever install a dead sink over the live one, and no late disconnect teardown can wipe the sink a fresh reconnect just registered. A blackholed sink = the member silently receives NO SyncPlay traffic until its next reconnect (the "got stuck / never started" failure). The Jellyfin `/socket` path uses the hub's per-device conn_gen; the native `/sync/v1/ws` path uses a process-wide monotonic counter.
- V31: the V19 per-member buffering freeze is BOUNDED — one member's `BufferingStart` may pause the group, but the group ALWAYS resumes. It resumes (a) the moment the last buffering member reports `BufferingEnd`/`Ready`, (b) immediately when the last buffering member LEAVES (socket drop / Leave / ghost-prune) without a `BufferingEnd` — a departing member must never own the freeze — or (c) after `BUFFERING_MAX_MS` (anti-wedge) if a member buffers forever without recovering, ending, or leaving. A group hydrated mid-freeze (rolling deploy) re-arms the anti-wedge deadline, since its restored members carry cleared buffering flags and can never fire the `BufferingEnd` auto-resume on their own. Mirror of V28's readiness-gate anti-wedge, for the buffering path.
- V25: a SyncPlay watch party survives a process restart / rolling deploy end-to-end, and the server NEVER silently drops a group command. Member ids derive deterministically from deviceId (same device → same member id across restarts); on /socket connect with no in-memory membership the server recovers it from the persisted `sync_groups` snapshots and resyncs the client; a command from a session with no recoverable group answers `NotInGroup` over the socket (stock jellyfin-web then visibly disables SyncPlay) — a silent drop lets the sender's local player apply the command one-sidedly (Pause pauses only the presser) and desyncs the party.
- V29: a trickplay sprite set counts as GENERATED only when its per-(media,width) `.complete` marker exists — written strictly after every sheet landed. Tile presence alone is a lie: the libav worker writes sheets straight into the served dir, so an interrupted run (op timeout, worker crash, deploy) leaves a truncated set that must be re-attempted, never advertised (grey previews past the truncation point otherwise). Marker-less sets are verified against the duration-derived expected sheet count (±1 trailing sheet for VFR/rounded durations): consistent → stamp marker; truncated → wipe + regenerate. Whole-file heavy-op timeouts scale with content duration (`max(900s, duration/2)`) — a fixed cap kills long movies partway. Image-subtitle burn-in uses the `overlay` filter_complex (the `subtitles=` filter is text-only and cannot render PGS/VOBSUB).
- V28: SyncPlay command scheduling is BOUNDED and gate ACKs are causally valid. (a) Clock samples with RTT > 10s are discarded at observe time (a throttled/suspended tab measures its own stall, not the network — its offset estimate is garbage too); (b) `lead_time_ms = MIN_LEAD + min(max_rtt/2, 2s)` — one member's pathological RTT must never schedule commands tens of seconds out for the whole group; (c) a readiness gate opened for a SCHEDULED command (Seek: clients execute at `When = at_server_ms`) ignores any `Ready` arriving before `at_server_ms` — it cannot be an ACK of a command nobody has executed yet; it's a spurious player transition. Counting it resolves the gate early, and the resulting Play broadcast makes jellyfin-web's `scheduleUnpause` CANCEL the client's still-pending seek callback (`clearScheduledCommand`), after which nothing ever seeks — `scheduleUnpause` only corrects players AHEAD of target, so everyone silently resumes from the pre-seek position.
- V27: every client-attributed SyncPlay report or request that names a queue entry (`Ready`, `Buffering`, `NextItem`, `PreviousItem` — all carry `PlaylistItemId`) is validated against the CURRENT queue entry before it acts. A stale-entry `Ready`/`Buffering` (the old episode's player transitioning during teardown, racing a queue change) must neither satisfy a readiness gate nor freeze the group — the sender gets a single-member PlayQueue catch-up re-send (same `LastUpdate`, so up-to-date clients drop it as a duplicate) and is expected to re-report for the right entry. A stale-entry `NextItem`/`PreviousItem` is a no-op (double-press / two-member race would skip an episode). jellyfin-web posts `Ready` on EVERY player transition, so an unvalidated gate is trivially poisoned by teardown transitions. Wire `UserLeft` carries the member's display NAME, never the member uuid.
- V30: the segmented-HLS surface (`/hls1/*.ts`) NEVER stream-copies video and never passes multichannel audio. `-c:v copy` per-segment HLS is structurally broken three ways: ffmpeg cuts copy output on source keyframes (durations drift off the uniform EXTINF grid), `-output_ts_offset` is silently INERT under copy (every segment restarts at PTS≈0), and passthrough/re-encoded multichannel AAC is undecodable in Firefox's MSE (fatal append on segment 0 — playback never starts; Chrome tolerates all three, masking the breakage). Every `.ts` segment: re-encoded H.264, `-muxdelay 0 -muxpreload 0` (default 1.4 s mpegts cue delay skews the anchor), `-output_ts_offset <start>`, AAC forced `-ac 2`. Copy remux stays legal ONLY on the progressive `/stream` path (one continuous output, no per-segment cuts). Corollary: any ffmpeg flag doing timeline/mux work needs a BEHAVIORAL test (run ffmpeg, ffprobe the output) — an argv-string assertion passes even when the muxer ignores the flag (B41 shipped exactly that way).
- V31: image-subtitle burn-in pays ONLY for segments the track provably subtitles. Every burn-capable request (live .ts, VP9 init/media, both prefetch paths) gates against the track's scanned event-window timeline (TinyOp::SubtitleWindows — packet demux, no decode; persisted per file+mtime+track via SubtitleKind::EventWindows); an event-free segment window (±500ms pad) strips the burn index, takes the plain fast path, and shares its cache key with subtitle-off playback. Gating is FAIL-OPEN: unknown/in-flight/failed timeline → burn conservatively — it may only remove provably-empty burns, never lose a visible subtitle. A nonexistent track index errors, never returns an empty (= never-burn) timeline. Prefetch re-gates per TARGET segment (the requesting segment's decision does not transfer on a sparse track). Any segment transcoding >3× its content duration logs WARN with full attribution (queue-wait/encode split, device, codec, burn, seek depth, source).
- V26: every server-side UserData mutation (mark played/unplayed, favorite/unfavorite, progress save, stop-finish) broadcasts a `UserDataChanged` frame whose `UserDataList` entries are FULL serialized `UserItemDataDto`s — `ItemId` in canonical 32-hex wire form, `Key`, `Played`, `IsFavorite`, `PlayCount`, `PlaybackPositionTicks`, `PlayedPercentage` (computed from runtime when known). jellyfin-web patches cards by `data-id == ItemId` and the detail page by `Key`, then applies the state fields in place — a bare `{ItemId}` stub or a decimal id matches nothing, so the UI only updates on manual refresh. Synthetic series/season ids cascade the mutation to every child episode and batch all changed entries (+ a folder entry keyed by the synth id) into ONE frame.
- V34: every heavy whole-file / whole-decode media source op (subtitle vtt/ass/srt extract, trickplay sprite generate, waveform astats, image poster/backdrop/attachment/font extract, any ffmpeg/libav source open) acquires a shared `bg_io` permit BEFORE touching the source — enforced by a `BgPermit` token in the fn signature, not by convention (an ungated call must not compile). Background sweeps ALWAYS gate; playback-priority "bypass" work (actively-watched item only, never a sweep) may run hotter but stays batched and yields to the metered live stream.
- V35: EVERY playback delivery path marks playback activity CONTINUOUSLY as bytes flow (metered body / lease refresh), never once-per-request — HLS `.ts`, progressive webm, direct-play + DirectStream `stream.{mp4,mkv}`, resume-from-offset, and all audio (`/audio/{id}/stream|universal`, remux). So the bg_io regulator parks the gate for the ENTIRE stream incl. a single long GET; `is_streaming()` is true for ANY active playback, not just segment-pulling clients.
- V37: `SupportsDirectStream` is advertised ONLY when pharos's verbatim `/stream` file plays as-is for THIS client — a real DirectPlay, or a webm-codec Matroska (VP8/9/AV1 + Opus/Vorbis) `deliver_stream` re-labels to `video/webm` for a client whose profile lists a matching webm DirectPlayProfile. `/stream` never remuxes the container or transcodes audio, so any remux decision whose raw file isn't playable (h264+eac3/ac3/dts Matroska) MUST carry a TranscodingUrl and NOT advertise DirectStream. Err toward transcode (always plays) over DirectStream (may be unplayable).
- V36: per-item asset generation opens the source ONCE per item — all subtitle tracks, all trickplay widths, all font attachments from one file open, never a loop of opens; and every on-demand extract (subtitle vtt/ass/srt, poster/backdrop/attachment/font, waveform) is cached AND single-flighted via a shared fetch-lock (get→lock→get double-check) so a cache miss can't fan into N concurrent whole-file demuxes of the same key. Fixed scratch paths are per-caller-unique. (Cache tier is per-cost: subtitle/image extracts are DISK-backed under the cache PVC — a once-ever cost surviving restarts; waveform is IN-MEMORY-memoised only, since its endpoint is client-optional and recompute is cheap.)
- V38: EVERY Jellyfin wire object a strict SDK (jellyfin-sdk-kotlin) deserializes is emitted from a typed `#[derive(Serialize)]` DTO, NEVER a raw `serde_json::json!` literal — so the kotlin-required-field contract is enforced by the type and a field-missing object cannot be constructed. Especially `/socket` broadcast payloads (`Sessions.Data[].NowPlayingItem`, remote/PlayState pushes), which bypass the audited `/Items` `BaseItemDto` path. Any embedded `BaseItemDto` (even minimal) carries its two no-default kotlin fields `Id` + `Type`; an unresolved `Type` OMITS the nullable item rather than emitting it Type-less.
- V39: A wire field typed as a kotlin ENUM (`PlaystateCommand`, `GeneralCommandType`, `PlayCommand`, …) may ONLY carry a value that is an exact member of that enum. A relayed/remote command whose value is outside the target enum is DROPPED (not forwarded), never emitted as a free string — an out-of-set enum fails the strict `kotlinx.serialization` decode and crashes a native cast TARGET (B79, same class as B78). Corollary: media-play is the dedicated `Play` MessageType (`PlayRequest`), not a `PlayState` `Command:"Play"`; `GeneralCommand` carries a non-null UUID `ControllingUserId` and a `Map<String,String>` `Arguments`.
- V40: No browser client is ever handed an unplayable stream with no fallback. Extends V37 to the DirectPlay VERDICT path: a DirectPlay / `SupportsDirectStream` result for a Matroska-container source to a browser (`<video>`/MSE, Mozilla UA) is honoured ONLY when the verbatim `/stream` relabel is `webm_relabel_playable` (webm-legal video AND audio that the client's profile lists); otherwise `playback_info` downgrades the `Decision` to a Transcode so a `TranscodingUrl` is emitted and SupportsDirectStream resolves false (B80). The B43 `force_webm` net is NOT relied on for this — it is off when `linux_firefox_h264=true` (B60). A genuine `webm` container is trusted (natively browser-playable + client-listed); only Matroska/MKV (the relabel hazard) is gated.
- V41: A client-supplied `ParentId` is matched in pharos's canonical dashless-32-hex wire form. `resolve_parent_filter` and `restrict_to_parent` canonicalise the id (`canonical_parent_id`: strip the dashes of an 8-4-4-4-12 hex UUID and lowercase; every other shape untouched) BEFORE any `== wire_id` / synth-hash / entity-store comparison, so a dashed UUID (jellyfin-sdk-kotlin / Android TV re-serialises every id through a `Uuid` and emits it dashed) resolves identically to the dashless form jellyfin-web echoes. A mismatch here silently falls to `Empty` — a blank library grid, no 4xx (B82). Extends the B15 inbound-id sweep (which canonicalised route-path ids via `parse_item_id` but left ParentId query-param resolution on raw string equality).
- V42: `/Items/{id}/Similar` ("More Like This") lists only items that share a REAL content-overlap signal with the target — same series, album, album_artist, genre, or immediate parent folder. Same media-kind alone is a tiebreak (sorts already-qualified ties kind-first), NEVER a qualifier: `similarity_score` adds its `+5` same-kind bonus only when the real-signal score is already `>0`, and `items_similar` keeps only `score > 0`. A thin-metadata library therefore returns a short or empty rail, never an alphabetical dump of every same-kind item (which surfaced unrelated content — an AWS training clip under "Back to the Future") (B83).
- V46: A movie/episode with NO sidecar `.nfo` still surfaces its embedded container description. The prober (both libav default + spawn) lifts `synopsis`/`description`/`comment` → `MediaProbe.synopsis`, `content_rating`/`rating`/`mpaa`/`law_rating` → `content_rating`, `network`/`publisher`/`studio` → `network`, and the full raw `date`/`originaldate`/`creation_time` → `release_date`; all four persist as `media_items` columns (round-tripped, migration 0041). The priority-30 `embedded` `MetadataProvider` (below NFO=100 / sidecar=50, above filename=10) maps them into the resolver merge → `Overview` / `OfficialRating` / `Studios` / `PremiereDate` (+ `ProductionYear` from `year`), so a user's curated NFO still wins every scalar but a sidecar-less file is no longer blank. A purely-numeric `content_rating` (an iTunes explicit-lyrics flag / star count) is dropped, not shown as a certification; a year-only `release_date` leaves `PremiereDate` unset. `PROBE_SCHEMA_VERSION` 4 re-probes existing rows so they backfill (B90/T100).
- V45: Every 200 image response (`/Items/{id}/Images/*`, indexed, chapter, and local-sidecar paths) carries a `Cache-Control: private, max-age=…` and a content `ETag` (file length+mtime), and a request whose `If-None-Match` matches the current ETag gets a bodyless `304 Not Modified`. All read paths funnel through one `deliver_image` helper so no image route can ship uncached. Rationale: before this, image responses set NO cache headers, so a gallery client re-downloaded every poster on every grid render / navigation — the posters-load-slowly complaint. 404 / person-redirect (302) responses stay uncached so newly-added art or a corrected redirect is not pinned (B89).
- V44: A video item's `Chapters` array carries a non-null `ImageTag` on every entry so a client renders the chapter thumbnail and fetches `/Items/{id}/Images/Chapter/{index}`; audio items (no extractable video frame) carry `ImageTag=null`. `image_tag_for(id, "chapter:{idx}")` mints the stable per-index tag; the `/Images/Chapter/{index}` route serves by index (ignoring the tag value) and extracts the frame on demand at the chapter's `start_ms`. A null/absent ImageTag makes chapters invisible — the client neither shows a thumbnail nor ever requests the image the handler is ready to serve (B88).
- V43: An episode list sorted by `SortBy=ParentIndexNumber,IndexNumber` comes back in air order (season then episode), never title order. The Jellyfin `ParentIndexNumber`/`IndexNumber` sort tokens are TYPE-OVERLOADED — season+episode for an Episode, disc+track for an Audio track — so `build_media_query` maps `SortPrimary::TrackOrder` to `(SeasonNumber, IndexNumber, Name)` when the query is episode-scoped (`kinds` contains `Episode`, OR the parent is a `Series`/`Season` pivot) and to `(DiscNumber, TrackNumber, Name)` otherwise. Mapping episodes onto the audio disc/track columns (NULL for episodes) collapsed every episode to the Name/Id tiebreak → an alphabetical-by-title list (Buffy S02E20 shown as the immediate next of S02E04) (B87). `SortKey::SeasonNumber` (`season_number`) is the new allowlisted column.
- V48: A DirectPlay/DirectStream `/videos/{id}/stream[.ext]` HEAD response reports the source's REAL byte length as `Content-Length` plus `Accept-Ranges: bytes`. A non-faststart mp4 (moov seek-index atom at EOF — most library files) is seekable only if the browser can learn the length to range-fetch the trailing moov; a zero/absent length collapses `seekable`→`buffered` (seek capped to already-buffered bytes). The HEAD is served via `actix_files::NamedFile` (body = `SizedStream`, `BodySize::Sized(len)`), NEVER a hand-built empty-body response carrying a manually-inserted `Content-Length`: actix's h1 encoder derives a HEAD's Content-Length from the body `BodySize` and DROPS the header, so an empty `()` body advertises `Content-Length: 0`. Sibling of V47 (the Range→206 half of Firefox seekability). Guard: jellyfin_stream.rs head_reports_real_content_length (B101).
- V49: Every live audio remux/downmix delivery (`/Audio/{id}/universal` → `audio_remux`) honours `StartTimeTicks` as an INPUT seek (`-ss` BEFORE `-i`). The output is a chunked ffmpeg pipe (no Content-Length, not byte-seekable), so jellyfin-web seeks by re-requesting with a fresh StartTimeTicks; ignoring it restarts the encode at t=0 and caps seeking to already-streamed audio. The ffmpeg argv is built by the pure `audio_remux_args` helper so the `-ss`-before-`-i` ordering is unit-asserted without spawning ffmpeg. Guard: stream.rs audio_remux_args_seek_is_input_option / audio_remux_args_no_seek_at_zero (B102).
- V50: Every HLS VOD playlist — video variant AND continuous-audio rendition — enumerates the FULL source timeline; its segment count derives from a duration resolved through `load_hls_item` (persisted probe → live-ffprobe fallback), never a `duration_ms.unwrap_or(0.0)` that a probe-missing row collapses to a single `.max(1)` 6 s segment (which caps seeking to the first segment). Guard: vp9_audio_rendition.rs audio_playlist_recovers_duration_when_probe_lacks_it (B103).
- V51: A library scan's mark-and-sweep of unseen rows is blast-radius-capped — it can never erase the catalog from a partial/failed source listing. `sweep_exceeds_guard(unseen, total)` BLOCKS (logs, no delete) a sweep that would remove BOTH >25% of rows AND ≥100 rows; a genuine large delete under the fraction cap still proceeds. A transient NFS mount that lists too few files while reporting `walk_errors==0` therefore cannot wipe the library (B98: 8192/13972 rows swept, Supergirl vanished). Recovery = fresh full mount + full scan (re-adds ungated). Guard: sqlite_store sweep_guard_blocks_catastrophic_mass_delete + sweep_guard_allows_large_delete_under_the_fraction_cap + small/large/fraction unit tests.
- V52: At most ONE library scan runs at a time; concurrent `/Library/Refresh` requests coalesce into a SINGLE pending re-run (force OR'd) that fires when the current scan finishes. `start_or_mark_pending` acquires the single slot or folds the request into the pending re-run; `finish_or_rerun` keeps the task Running across the re-run so there is no Idle gap a concurrent start could exploit; a cancelled pass never re-runs; the coalesced re-run rescans the full current media-root set. Prevents N concurrent full NFS catalog walks I/O-starving the node (B100: ~10 stacked scans → apiserver ServiceUnavailable). Guard: scan_tasks concurrent_starts_coalesce_into_one_pending_rerun + a_lone_run_with_no_pending_finishes_to_idle + a_cancelled_pass_does_not_rerun_even_with_pending.
- V53: Subtitle delivery is decided from the CLIENT's declared `DeviceProfile.SubtitleProfiles`, never a fixed text→External/image→Encode rule. A text/ASS format the client cannot render externally (absent from its SubtitleProfiles, or declared with a non-external method — e.g. the Jellyfin Android app, which omits ass/ssa by default) is BURNED into the transcode (`DeliveryMethod:"Encode"`, no DeliveryUrl, `SupportsExternalStream:false`); a client that lists the format External (jellyfin-web + SubtitlesOctopus) still gets the raw `Stream.ass`. When the selected (or default-disposition) subtitle must burn and the video decision is DirectPlay/DirectStream, `playback_info` downgrades it to Transcode so a burn always has a video stream (extends B80/V40 to the subtitle-selection path). The burn rasterizes text via the ffmpeg `subtitles=` filter reading the pre-extracted disk-cached `.ass` sidecar + a `fontsdir` of pre-extracted embedded fonts (NEVER the whole source per segment — that re-demuxes the NFS file + re-extracts fonts every 6 s, the documented stutter class), timestamp-aligned per segment via `setpts=PTS+start/TB, subtitles, setpts=PTS-start/TB` (the sidecar keeps absolute event times; `-copyts` is wrong — it collapses `-t`). Image (PGS/VOBSUB) burn stays on the `overlay` filter. Guards: subtitle_delivery unit tests, jellyfin_playbackinfo_subtitle_burn (Android burns / web stays External / DirectPlay downgrade / explicit-off stays DirectPlay), subtitle_burn_ass.rs behavioral (cue rasterizes at the correct absolute segment, from a standalone sidecar).
- V54: On the VP9/fMP4 path the separate continuous-audio rendition anchors its seek to the SAME frame-snapped grid the video segments use — `audio_seg_start_secs(seg, fps)` mirrors `segment_start_secs = round(seg*6.0*fps)/fps` — for BOTH the `-ss` input seek and the `-output_ts_offset`, and its playlist EXTINF is frame-aligned via `segment_time_range` like the video variant. Anchoring audio to the nominal `seg*6.0` while video sits on the frame-snapped grid leaves a fixed sub-frame A/V skew injected at every mid-file audio-track switch on a non-integer-fps source (B105). Any change to the audio seek anchor bytes bumps `HLS_GEN_VERSION` to orphan stale `_audiohls` dirs. Guard: hls_cache.rs audio_hls_args_seek_anchor_is_frame_snapped_to_video_grid (seg1 @ 23.976 fps → `-ss 6.006` + `-output_ts_offset 6.006`, never 6.000).
- V55: A mid-file audio-track switch seeks the audio rendition straight to the playhead, never re-encoding 0→playhead first. The rendition is one continuous ffmpeg run to EOF (no `-t`, `-hls_list_size 0`), so `want_seg` only governs WHEN a segment appears; the pure `choose_audio_start_seg(want_seg, from0_active, seek_progress)` reserves the whole-file from-0 session for a genuine start-of-file request, reuses a running from-0 session only within the near-start lookahead window, reuses a running seek session within its lookahead, and otherwise starts AT `want_seg`. - V58: Speculative transcode work NEVER takes capacity a client request needs, and is DEFERRED rather than DROPPED. Every segment mint carries a `JobClass` (`Interactive` = a client response is blocked on it; `Background` = prefetch / prewarm). A `Background` job takes a permit only while more than `background_headroom` (default 1) permits are free across the devices that could take it — and only on a device not already carrying a client's segment past its learned allowance (V125). When that candidate pool's whole capacity is no larger than the reserve, the job is SHED (`SchedError::Busy`) rather than queued: free permits can never exceed the reserve there, so queueing would leave the caller's `submit().await` waiting on a condition that cannot arrive. It was once clamped to capacity minus one instead, which also resolved the caller but disabled the reserve entirely on a one-permit pool — `min(1, 0) == 0` — letting speculation take the only permit a client needed, and a pinned shared-init rendition (V80) resolves to exactly one device, so one-permit pools are not hypothetical. Refused for want of a free permit, it waits: it enters `pending` and is reconsidered on every freed permit, and when the queue is FULL the LEAST urgent speculative job in it is evicted to make room, not the arrival refused. A full FIFO rejects the newest arrival, and for prefetch the newest arrival is systematically the MOST urgent thing present — speculation is submitted in playback order, so the job arriving now is close to the playhead while the incumbents are the deep guesses submitted when the client was further back. The victim is chosen by the SAME key that ranks dispatch, read at its maximum instead of its minimum, so the queue can never evict a job it would have been happy to dispatch and passed work goes first (eviction runs on arrival, between drains, so it sees passed jobs no drain has yet dropped). Only `Background` is evictable — somebody is blocked on every Interactive job in the queue — and the arrival must actually BEAT the victim, so a burst of far-out prefetch cannot churn the queue and an arrival deeper than everything queued is refused instead. `pending_cap` still bounds the queue's SIZE exactly as before; what changed is which job leaves when it is reached. An evicted job's `oneshot` is resolved with `SchedError::Busy`, never merely dropped. A queued job whose caller has gone is swept from `pending` at the start of every drain, not only when it is selected — otherwise abandoned prefetch (every seek and every track swap orphans a window of it) occupies the shared `pending_cap` until the pool goes quiet, which is exactly when that cap is client backpressure. Already-passed work (negative lookahead distance — the viewer went by while the job waited) ranks BEHIND all live speculation rather than ahead of it; ordering on the raw signed distance would make the most useless job in the queue the most urgent one. It is also DROPPED rather than encoded: nobody will ever fetch those bytes, and encoding them spends a permit and, on a saturated pool, a client's place in the queue. `reply.is_closed()` does not cover it — only a seek or a track swap CANCELS a prefetch; a client simply advancing past it does neither. The drop is an UNCONDITIONAL SWEEP at the top of every drain (`reap_stale`), beside the abandonment sweep and for the same reason: selection sorts outrun work last by design, so a job in that band is examined only once it becomes the minimum, and under sustained load every freed permit goes to a live job and the drain exits with the band untouched. Dropping only what selection happens to examine leaves stale work occupying `pending_cap` — client backpressure — until the pool goes quiet, and biases the signal too: a stale job that eventually leaves by eviction is counted `evicted`, so the `stale` arm under-reported precisely under saturation, the only load at which anyone reads it. The sweep BOUNDS that bias rather than closing it: a job that turns stale between two drains and is chosen as a victim before the next one still leaves as `evicted`, because the sweep cannot see a job that is no longer in `pending`. The window is now one freed permit instead of one quiet pool, and the two arms are read together when the question is how much speculation was wasted. Because a playhead moves only inside a message arm — an interactive `Submit`, or a `Playhead` reporting a cache hit — and the actor processes no messages mid-drain, no job can become stale between the sweep and selection, so the passed band is unreachable from selection and is read only by the eviction victim choice — which is where a job that turned stale between drains is caught. The arrival path (`place`) never checks staleness and cannot need to: a job's arrival IS its submission, so a `Background` job that arrives behind its stream's playhead is a deliberate backward guess, not a leftover. The boundary is STRICTLY negative. The lookahead distance measures against the last segment the client ASKED FOR, not the last it finished, so distance 0 is the segment being fetched right now — wanted, in progress, not yet produced — and it is the segment selection ranks FIRST among speculation; treating it as passed would have the queue destroy the job it had just called the most urgent thing in it. `i64::MAX` (no playhead, or a job that is not a numbered segment) is not passed either: nothing is KNOWN to need it, which is not the same as knowing nothing does. Behind the playhead is NOT the same as outrun, and only outrun work may be dropped. The SyncPlay seek prewarm submits `Background` for the seek TARGET on a member's EXISTING stream, before that member's own interactive request moves the playhead there, so a backward group seek makes every one of its jobs negative the instant it arrives; a drop keyed on the sign alone deleted that shipped feature, load-dependently (with a free permit the same job goes straight through `place`, which never checks) and with no trace but a `stale` increment indistinguishable from a wasted guess. Each job therefore freezes the VALUE its stream's playhead stood at when it was ADMITTED, and stale is `seg >= head_at_submit AND seg < head_now` — in front of its viewer when the job was made, behind them now. The TICK at which the playhead was last set will not do, though it reads like the same question: `note_playhead` bumps that clock on EVERY interactive submission whatever it does to the position, so a member still playing FORWARD while the prewarm for its own seek target waits — the ordinary shape, since the prewarm fires the moment the seek is dispatched and the member applies it seconds later — moved the tick and condemned the prewarm. The value is strictly stronger: a real overtake always changes it, so every genuinely outrun job still dies, while a job submitted behind its viewer is never stale however the playhead subsequently moves. A backward guess the group then changes its mind about is CANCELLED rather than swept, by the mechanism that already covers it: a seek or a track swap closes its `oneshot` and the abandonment sweep collects it. That mechanism is NOT free once the segment cache drives its encodes on a DETACHED task (V126/006 phase 2a), and it stopped being true for a release: `PrefetchRegistry` cancels by aborting the spawned prefetch task, which then killed only the WAITER while the `oneshot` lived on inside the driver, so `reply.is_closed()` was false for every abandoned prefetch and this clause described nothing. An episode swap left roughly 6-14 orphaned encodes for the previous episode draining onto the GPU exactly as the new one started — bounded to `allowance` concurrent jobs by V125, so waste rather than outage, but waste at the worst possible moment and a fix that had already been made once. A detached encode therefore outlives the requester that STARTED it and not the last requester WANTING it. The registry holds the publish channel's SENDER and no receiver, so its receiver count is exactly the number of requesters still waiting; the driver races `produce_segment` against that count reaching zero, and the losing branch drops the produce future, which drops the `submit()` inside it and closes the `oneshot` the sweep reads. `tx.closed()` alone will not do — a bookkeeping receiver held by the registry would sit in the count forever, and a joiner may `subscribe` after the wake, so the decision is retaken in a loop. The abandonment is DECIDED under the map's shard lock (`remove_if`, qualified by a registration id so a driver can only ever deregister itself): a joiner's registration takes the same lock, so either it subscribed first and the encode continues, or it cannot find the entry at all and drives a fresh one, and no interleaving leaves a live requester waiting on an encode that has decided to stop. What that reclaims is the QUEUED population and nothing else. A job the scheduler has already handed to a worker cannot be given back: `spawn_run_task` is a detached task owning the worker AND the device permit, the `JobFinished` arm ignores a failed reply send, and every `reply.is_closed()` read (`place`, `reap_abandoned`, `try_place_no_queue`) is PRE-dispatch — so a dispatched job runs to completion however the caller feels about it, and abandoning one spends the encode and then throws the bytes away. The cancellable region therefore ENDS AT DISPATCH (`JobSlot::is_dispatched`, latched by the scheduler at the one place a job takes a permit), which costs zero reclaim, keeps the bytes of an encode the GPU has already been spent on, and makes this clause true by construction rather than approximately. It also removes a hazard the wider region carried: a cancelled-but-DISPATCHED orphan keeps writing to `{seg}.ts.tmp` and its `-progress` sidecar, both deterministic and key-derived, so a fresh requester for the same key starts a second worker on the same two files — and `read_progress` CONSUMES the sidecar while `short_of_frames(None, _)` fails OPEN, so the completeness gate can be defeated by the collision and `rename` then publishes an inode the orphan is still writing into: a corrupt segment, cached, and served with a 200 for as long as it stays on disk. The triggers are ordinary — a page refresh during a cold start, an `hls.js` `fragLoadTimeout` retry, a swap-and-swap-back. The dispatch flag is latched inside the actor's dispatch step and read outside it, so a crossing the width of an atomic load survives; each registration therefore writes to `{seg}.{registration}.ts.tmp`, which makes that crossing cost an unreferenced temp file instead of a corrupt segment. Cancellation stops at the RENAME as well, which is the same boundary for the path that has no scheduler: a cancellation landing between `outcome="ok"` and the LRU `record` counts ONE attempt twice — breaking the partition this clause invokes — and leaves a published `.ts` that `total_bytes` never learns about, so it is never accounted and never evicted. And the decision to stop is only ever taken while this driver's OWN registration is still in the map: an entry that is absent, or a successor's, means there is nothing left that could wait, and reading that as "somebody is waiting" re-enters a loop whose `tx.closed()` is already resolved — an infinite loop with no await point in it, inside one poll. An encode stopped this way is counted `pharos_segment_produced_total{outcome="cancelled"}` — a production attempt that ended without a segment is still an exit, and V128 requires the arms to partition. The counter says how many encodes were ABANDONED, which is not the same number as capacity returned: only the queued share of it ever held a permit to give back. Guards: hls_cache.rs an_encode_nobody_is_waiting_for_is_cancelled_rather_than_run_to_completion, cancelling_the_first_requester_does_not_abort_the_encode, a_dispatched_encode_survives_its_last_requester_and_reaches_the_cache, two_registrations_for_one_key_never_write_the_same_file, a_driver_whose_registration_vanished_stops_instead_of_spinning; scheduler.rs a_slot_says_when_its_job_is_past_reclaiming. A stream with NO reading at admission is not a deliberate backward guess — nobody chose to aim behind a playhead they could not see — so an ordinary prefetch that had no reference still dies once the client turns out to be past it. Surviving the sweep is not sufficient on its own either, because MAGNITUDE decides everything within a band: a deliberate backward guess takes magnitude ZERO rather than its absolute distance, so it is dispatched FIRST and evicted LAST. Ranked by `abs`, a guess at −400 was the deepest thing in the queue, so the seek target was dispatched after every forward prefetch — i.e. encoded after the member had already arrived at it, the feature defeated with nothing dropped and no counter moving — and was the preferred eviction victim for the next arrival with any smaller magnitude. Ranking, dropping and the eviction victim choice share ONE predicate (`is_stale`) so the three cannot drift into different opinions about the same number. Unknown urgency (`i64::MAX`) is handled in two places rather than one, because a single total order cannot both defer it last and destroy it first. A speculative submission may SEED a playhead only where no reading exists AND only if its CALLER claims to know where that stream's playback begins (`JobHint::seeds_playhead`, set by the two prewarms — which pick their base from the resume position or the group's seek target — and by nothing else) — seeding cannot MOVE an existing reading, so no active viewer's lookahead can measure itself, and without it the cold-start prewarm (`prewarm_cold_start` submits against a brand-new `StreamKey` no interactive request has touched) was unknowable for its whole life and so refused at a full queue, or admitted and evicted first, losing a new viewer its opening segments to a guess a minute ahead of somebody already playing. The entitlement may NOT be inferred from the playhead map having no entry, which looks equivalent and is not: a stream has no entry until something has been SERVED on it, so an ordinary deep prefetch can be the first thing submitted for one — and letting that seed puts a guess back to ranking itself, in bounded form. A reading moves on an interactive `Submit` OR on a segment the cache served without the scheduler seeing a job for it (`SchedMsg::Playhead`, sent by both hit paths in `segment_bytes_keyed` for an `Interactive` request on a named stream, T109). Reporting hits is not optional polish: a viewer with a warm buffer takes fast and coalesced hits and nothing else, so a reading only a MISS could move went stale in proportion to how well prefetch was working, and `next_to_dispatch`, `is_stale`, `queue_or_refuse` and `pharos_transcode_queue_distance` were all wrong for that stream in the same direction at once. The two writers carry different evidence and obey different rules. A SUBMISSION may move a reading in either direction — that is how a backward seek is expressed, and the only way it can be. A HIT may only ADVANCE one: it says the viewer REACHED that segment, never that they returned to it, and it lands when the bytes were read rather than when they were asked for, so an out-of-order hit for N after a request for N+2 must not drag the reading back. A hit on a stream with no reading establishes one — a hit is a client's own request, not a guess, so it carries exactly the entitlement an interactive `Submit` does. Not covered, knowingly: a rewind landing on a segment still in the cache is a hit, so the reading stays where the viewer was; that is what the miss-driven map did too, and following it back needs the request's arrival instant carried on both messages so the map is written in request order. The send is synchronous and fire-and-forget (`try_send`) because a hit is the common case and the path holding a viewer's segment response must never wait on the actor; a full inbox DROPS the update, which is safe by construction (a lost reading is exactly as stale as before this existed, never staler) and is counted on `pharos_transcode_playhead_dropped_total`, since a reading that stopped moving otherwise cannot be told from a saturated inbox. What is genuinely unrankable — no stream, or not a numbered segment — is excluded from eviction CANDIDACY for a speculative arrival: deferring unknown work costs latency, destroying it is irreversible, and a guess may not buy its slot with work it cannot compare itself against. A CLIENT'S arrival may still displace it, or a queue of unrankable speculation would become unevictable and start shedding interactive requests. Selection happens at DISPATCH, not on arrival: every Interactive job before any Background one, Interactive among itself in arrival order, Background among itself by ascending lookahead distance recomputed against that stream's current playhead — a job queued at distance 6 is distance 1 once its client has consumed five segments, and freezing urgency at submit time ranks that exactly backwards. THIS REVERSES THE ORIGINAL RULE, WHICH WAS "NEVER QUEUES", AND THE ORIGINAL RULE WAS CORRECT FOR THE CODE IT WAS WRITTEN AGAINST. B108 happened: a queued prefetch held the segment cache's per-key fetch lock across its whole scheduler wait, so a client asking for that same segment inherited the entire wait the prefetch existed to spare it, and a 3.4 s encode became a 90 s stall. Two things changed. The per-key lock is gone — requesters coalesce onto a shared RESULT and nothing holds exclusion across an encode — so a queued job cannot block anybody on a lock. And a client that coalesces onto speculative work PROMOTES it (`SchedMsg::Promote`): a client waiting on a guess's result is proof the guess was right and proof it is no longer a guess, so it is re-ranked as the client's own work rather than leaving that client behind every other client's. Promotion does not move the stream's playhead — a joiner is waiting on that segment, not standing on it — and does not start a second encode. It also survives the `-progress` completeness retry, which re-submits under a NEW job id that no joiner will promote a second time: the cache records that a client joined (`InFlightSegment::promoted`) and the driver re-submits at the promoted class, because "a client is waiting on these bytes" outlives the individual job producing them. Without promotion, deferral is not permitted: dropping the work is better than making a client wait at a speculative tier, and the fallback is urgency-gated admission with no queue at all (admit at lookahead d iff free background slots >= d). Deferral and shedding are both reported as themselves, never as breakage — distinct `HlsCacheError::SchedulerBusy`, DEBUG log, `pharos_segment_produced_total{outcome="shed",reason="scheduler_busy"}`, `pharos_transcode_promotion_total{outcome}`, `pharos_transcode_queue_outcome_total{class,outcome}` (and `pharos_transcode_queue_distance`, which takes no sample from a backward guess: that distance is a property of how far a viewer seeked, not of the prefetch ladder the histogram exists to describe, and a positively-bounded histogram folds every such sample into its bottom bucket and reads the healthy verdict back precisely while a group is seeking) — because deliberate load management logged at ERROR drowns the real failures beside it, and logged nowhere is indistinguishable from silence. A speculative job's long-wait warning uses its own much looser threshold: prefetch is now SUPPOSED to wait, and judging it at a client's bar would bury the client-side signal that warning exists for. Keying them apart does not merely waste disk: the single-flight lock in `HlsSegmentCache` is keyed by exactly this identity, so two keys mean two concurrent transcodes of byte-identical output, doubling GPU + NFS load mid-playback. Guards: `an_audio_free_segment_is_not_keyed_by_the_audio_track` (same key, filename AND etag) and its converse `a_muxed_segment_is_still_keyed_by_the_audio_track`, which fails if the collapse is applied blanket and one track's bytes are served under another's request.

- V64: A wait on a producing session distinguishes SLOW from DEAD, and says which. `audio_hls_file_budget`'s stall budget is an inter-segment interval, not a latency budget — a continuous audio session emits one segment at a time, so the budget must exceed `SEGMENT_SECONDS` with margin or ordinary I/O contention reads as a wedge (asserted by `the_stall_budget_outlasts_a_realtime_audio_session`, not left as a hand-tuned number). Progress is read from the sessions that could actually SERVE the request (starts `<= want`, mirroring `resolve_audio_file`), and reports "not started" while the deepest of them has written nothing — a global high-water mark denied a freshly-spawned seek session the cold-start grace that existed for exactly its window (`a_fresh_seek_session_still_gets_the_cold_start_grace`). When it does give up it names WHICH budget expired via `AudioWaitGiveUp`, carried in `HlsCacheError::AudioNotReady` through to the HTTP body, counted as `pharos_audio_wait_total{outcome}` on BOTH outcomes, and logged with the same fields. Corollary, same discipline: `out_bytes` is recorded only when the sink can measure it — a live-stream job's bytes go down the pipe, and reporting the unmeasured count as `0` made a healthy encode indistinguishable from a silent empty one (`only_a_file_sink_claims_to_have_measured_its_output`).

- V65: A SyncPlay member with NO SOCKET is awaiting a reconnect, not haunting the group, and is judged on `DISCONNECTED_TTL_MS` (10 min) rather than the ghost `MEMBER_TTL_MS` (150 s). The two describe opposite situations: a member silent WITH a live socket is a dead client holding a place in every readiness gate and must go promptly; a member whose socket is gone already holds nothing (`follower_ids` filters on `connected`), so an early prune achieves only the destruction of a membership its client is mid-reconnect to. A member hydrated by `apply_persist` is therefore restored `connected: false` — this replica has never seen its socket — which is both truthful and what makes the longer grace safe. Guards: `a_disconnected_member_survives_long_enough_to_reconnect` (survives past the ghost TTL, healed by a late `ResyncMember`) and `a_disconnected_member_that_never_returns_is_still_pruned` (the grace is a grace, not an amnesty).

- V66: Route registration order IS the routing decision between patterns of the same arity. Actix takes the first registered pattern that matches; a literal segment does NOT outrank a parameter. So `/items/{id}/images/chapter/{image_index}` must be registered BEFORE `/items/{id}/images/{image_type}/{image_index}`, or every chapter request is swallowed by the generic handler and answered `400 unknown image type` from a route the request never reached. Guard: `jellyfin_chapter_image_route.rs` drives the REGISTERED app (a shadowed route is invisible to a test that calls its handler directly) and distinguishes the two answers — 404 "chapter index out of range" proves the request arrived, 400 proves it was shadowed — plus a converse test that the generic indexed route still dispatches and still rejects a genuinely unknown type.

- V67: A produced segment is measured against the frames its window IMPLIES, not merely against a fraction of its duration. `SegmentWindow` keeps the `FrameRate` it was snapped to, so `expected_frames()` can count the frames presented in `[start, end)` — with `ceil`, not `round`, because the bounds carry the half-frame seek bias and both ends land on exactly `n + 0.5` frames, where `round` would decide a frame's ownership on the last bit of a float. Segments legitimately alternate 143/144 frames at 24000/1001 (the grid is a 6.000 s nominal snapped to frames, not a 6.006 s stride), so the asserted invariant is that adjacent windows TILE and account for every frame exactly once, not that each holds the same count; abutment is compared in TICKS, since a window stores its bounds at 100 ns resolution and consecutive segments may differ by that last unit. An unknown source rate yields `None`, never a guess, so an unprobed source cannot manufacture a phantom deficit. Every cache miss reports `expected_frames`/`produced_frames`/`frame_deficit`/`produced_secs` and counts `pharos_segment_frames_total{result}`; a shortfall warns. This exists because the pre-existing completeness check could only see a segment that missed 10% of its duration — 600 ms at 6 s, ~14 frames — so a stutter-scale shortfall passed as healthy, was cached, and replayed on every later view. Guards: `a_window_knows_how_many_frames_it_implies`, `a_window_with_no_known_rate_implies_no_frame_count`, `a_segment_missing_frames_is_measurable_even_though_the_gross_check_passes`.

- V68: A segment's audio source is settled BEFORE it can be lowered, and the type says so. `SegmentOpts` is the request and carries no audio-source field; `ResolvedAudio` is the settled answer, whose `Muxed(codec, slice)` variant cannot be constructed without the slice; `ResolvedSegment` is the only thing with a `to_transcode_options`. `SegmentOpts::resolve`/`resolve_with` are the only constructors and run the caller's closure for exactly the deliveries needing a slice, so it cannot be skipped, forgotten, or passed as `None`. Two fields describing one decision is what broke: `muxed_audio_source: Option<MuxedAudio>` sat beside `audio: AudioDelivery`, they were free to disagree, and when they did the argv fell through to `-an` and shipped video-only segments. Applying this found a SECOND instance the runtime fix had missed (the uncached live fallbacks in `hls_segment` and the VP9 path, which have no cache to produce a continuous encode and now say so with the reason) and a test asserting a contradiction (`segment_frame_completeness` declared `Muxed` with no source, so it had been encoding video-only all along). Guards: `a_resolved_muxed_segment_copies_its_audio_and_never_drops_it` and `only_a_muxed_segment_asks_for_a_continuous_audio_slice`. The old test that pinned the broken argv can no longer be written — it does not compile — which IS the invariant.

- V69: Where a client dialect has two legal spellings of one request, pharos serves BOTH. Chapter thumbnails are addressed `/Images/chapter/{n}` by jellyfin-web and `/Images/chapter?imageIndex={n}` by jellyfin-sdk-kotlin (Android / Google TV); serving only one 400s an entire client's chapter strip. Both spellings route ahead of every `{image_type}` pattern of the same arity (see V66) and share one `serve_chapter_image`. Guards: `a_chapter_image_request_reaches_the_chapter_handler` and `the_kotlin_sdk_chapter_spelling_reaches_the_chapter_handler`, both driving the registered app.

- V70: A per-segment video encode is pinned to the SOURCE frame grid on EVERY device. The software encoders take `-enc_time_base 1:90000`; the hardware encoders reject it and take `-r <source rate>` instead, which `SegmentWindow` makes possible by keeping the `FrameRate` it snapped to and lowering into `TranscodeOptions::source_frame_rate`. Without one of the two an encoder quantizes the zero-based first-frame pts to its default 1/framerate timebase, places the first frame half a frame late and loses the last — exactly one frame per segment. `-fps_mode passthrough` is NOT a substitute: it restores the frame count while still leaving a one-frame gap at the join, i.e. it fixes the number and not the tiling. `-r` is emitted only when the rate is genuinely known, because a guessed rate resamples the picture. Guards: `a_hardware_segment_encode_is_pinned_to_the_source_frame_grid` (hardware gets `-r 24000/1001` and no `-enc_time_base`; software keeps `-enc_time_base` and gets no `-r`) and `an_unknown_frame_rate_pins_nothing`.

- V71: `MuxedAudio::start_seconds` is where the FILE actually starts, never where its session was asked to start. A segment slices the continuous encode with `-ss (input_seek - start_seconds)`, and `-ss` on an input is measured from THAT INPUT'S OWN START TIME, so any error in the field shifts the audio under the video by exactly that much. The two coincide only for sources whose audio stream begins at 0: a from-0 session on a source whose audio starts late produces a file whose first sample is at the stream's own start (ffmpeg preserves it — verified by running the production argv against the real file), while the session records `0.0`. `ensure_continuous_audio_covering` therefore PROBES the produced file's first audio packet and records that, cached per session file, falling back to the requested start when the file cannot be probed yet. A session that does not start where it was asked to logs the skew at INFO. Guard: `the_slice_seek_honours_the_files_true_start_not_its_requested_one` asserts BOTH directions — true start puts the tone under the right video, `0.0` shifts it a whole segment early — with a short tone placed just past a segment boundary, because a wide tone cannot separate the cases (the first version of that test used a 2 s tone against 6 s segments and passed against the bug).
- V72: the demuxed audio rendition must sit on the SOURCE timeline, in content and in anchor, and neither half can be assumed from the other. Content: ffmpeg re-bases the only mapped stream so its first sample sits at zero, discarding an audio track's own start time, so the whole-file session is padded by that start (`-af adelay`) — measured on ffmpeg 8.1, `-output_ts_offset`, `-copyts` and `-avoid_negative_ts disabled` all leave the content where it was, and a SEEK session needs no pad because `-ss X` lands on source X exactly. Anchor: ffmpeg's HLS muxer numbers each session's `tfdt` from that session's own first fragment whatever it is passed, so a fragment is shifted by its producing session's start when served, which is the only place that start is known. Guards: `a_late_starting_audio_track_still_lands_under_its_own_video` DECODES a fragment and locates a known beep (a header assertion cannot see a content shift, and asking for the segment directly spawns a seek session that lands honestly and would test nothing — the test must request segment 0 to exercise the whole-file session); `shifting_moves_every_tfdt_by_the_same_delta` and `a_seek_sessions_fragment_reports_the_session_it_came_from` pin the anchor.
- V73: the tracks a client is told to start on are the user's, not the container's. Order: an explicit pick on THIS request; then the track that user last played this item with (`RememberAudioSelections` / `RememberSubtitleSelections`, including a remembered `-1` = subtitles off); then Jellyfin's selector over the user's `AudioLanguagePreference` / `PlayDefaultAudioTrack` / `SubtitleMode` / `SubtitleLanguagePreference`. The selector is a faithful port of `Emby.Server.Implementations.Library.MediaStreamSelector` — including the trap that a container's default-flagged track BEATS the language preference while `PlayDefaultAudioTrack` is on (Jellyfin's default), which is why Aliens keeps playing Ukrainian until that setting is turned off. Faithful because the settings are configured from stock jellyfin-web: pharos must do what that UI describes, so upstream's own score table and audio-selection vectors are asserted digit for digit. `OriginalLanguage` ranks by the title's own `original_language` (recorded by enrichment from TMDB), degrading to no preference — never to a guessed language — for an item nothing has enriched. A progress report that does not name tracks never erases a remembered choice: both the write path and the UPSERT `COALESCE` onto the stored value.
- V74: a landscape image is chosen art before it is an extracted frame, and the picker offers only what can be stored. Neither online provider publishes a thumb image type — TMDB's `/images` carries `posters` / `backdrops` / `logos`, TVDB the same — so a Thumb has exactly three sources, in order: the item's own Thumb row (a `landscape.jpg` sidecar or an episode still), then its Backdrop, and only then a frame extracted at `image_seek_seconds`. The frame is last because nobody chose it: on a film with a dark opening it is the title card. `pharos_image_thumb_source_total{source="artwork"|"backdrop"|"frame"}` counts which answered, so the items still falling to a frame are countable rather than merely visible. The same substitution runs in the online picker — a `Type=Thumb` search offers the backdrops — but ONLY for a real `media_items` row: `series_metadata` records a poster locator and a backdrop locator and nothing else, so a container's Thumb pick could not be persisted and is refused rather than half-applied.
- V75: a detector's silence must be explainable. Intro/outro detection finding nothing is the COMMON case — most shows have no shared intro — so a season that emits nothing is indistinguishable from one whose segments were found and discarded unless the gate's inputs are recorded: `detect_season_verbose` keeps every episode's `matched` / `agreeing` / `confidence` and the `Verdict` that rejected it, `detect_season` is a filter over that, and the backfill logs the per-season counts plus each dropped episode's own numbers and counts them as `pharos_segment_detect_total{kind,outcome}` from a `label()` method. Agreement is scored against the comparisons that LOCATED a span, never against every peer in the season: a peer that aligned nothing offered no evidence, and dividing by it made recall fall as a season grew longer. And the analysis is stamped separately from its result (`media_segment_scans`), because an empty detection writes no segment row — conflating the two re-analysed every intro-less season on every pass forever AND left a version bump unable to reach an episode with no row to carry a version. The fingerprint version and the detection version are distinct: a consensus change must re-run pairwise comparison over cached points, not re-decode the library.
- V76: an `ImageTag` is a VERSION, not an identity. The tag is what a client compares to decide whether to re-fetch, and images are served `Cache-Control: private, max-age=604800`, so a tag derived only from (item id, role) pins a browser to whatever it cached for a week — a picked, uploaded or deleted image overwrites the item's deterministic cache slot and produces the same URL, which is never revalidated. The premise that made that safe (an image is a deterministic re-extraction, so its identity IS its version) stopped being true the moment art could be REPLACED. `media_items.art_version` is therefore an input to `image_tag_for` alongside the item and the role, and every path that replaces bytes under an existing slot bumps it: the RemoteImages download, the manual upload, the delete. `set_artwork` deliberately does not — the scanner re-records identical sidecar paths on every pass, and a tag that rotates when nothing changed is a cache-buster, not a version. The ETag is not a substitute: it was correct and did change throughout, and was never consulted, because a client that believes its copy is fresh sends no request to attach it to.
- V77: a poster is asked for by the role the CLIENT requests, and a provider is asked until one of them answers. An episode's still is its `Primary` — Jellyfin's episode tiles request Primary and nothing requests an episode Thumb — so filing a still under Thumb enriches an episode into a state where it still advertises no poster and falls to a frame. A show's `/series/{id}/extended` body carries `artworks[]` alongside `data.image`, so the backdrop and logo come from the response already in hand, chosen by best community score, rather than being left absent. And no single provider is authoritative: TVDB declining a title is not evidence the title is unmatchable, so TMDB is tried after it — with a provider ERROR kept distinct from a genuine no-match, because collapsing the two writes `none` and freezes the show for the refresh TTL on the strength of a blip. Beneath all three the frame extract remains, and it is the LAST resort by construction: nobody chose it, so anything that reaches it is a gap to be counted, not a result.
- V78: a rendition's segments and its init share ONE clock, and that clock is a property of the output format — never of the device that happened to be free. Every fMP4 segment is muxed on `FMP4_TRACK_TIMESCALE` (90000, the MPEG clock the mpegts segments already use), pinned at the muxer with `-video_track_timescale`, because the encoder-side frame-grid routes legitimately differ per device (`-enc_time_base 1:90000` for software, `-r <source rate>` for hardware — V70) and the muxer would otherwise inherit whichever ran. A segment on a different timescale is not rejected by anything downstream: the player divides it by the init's timescale regardless and lands the whole fragment at `actual/expected` times its true position. So each produced segment is judged against the pin and counted as `pharos_segment_timescale_total{verdict}` from a `label()` method, with the offending timescale in the log line rather than a bare class, and the init route is judged too — an init on the wrong clock mis-reads every segment that follows it. Frame completeness (V67) cannot stand in for this: it passed on every affected segment, because the encoder produced exactly the frames asked for.
- V79: a title-match score treats an appended tail as evidence RETAINED, not evidence against. `title_similarity` scored a local name against a provider's canonical title as pure length-normalized Levenshtein, so a provider that appends a subtitle (`Code Geass` vs `Code Geass: Lelouch of the Rebellion`) or a local name that adds a qualifier (`Forever (US)` vs `Forever`) drove the edit distance up in proportion to the length GAP and sank the score below the `match_min_confidence` floor (0.7) — recording the show `none` with no poster, no backdrop and no episode stills, exactly the shows V77's TMDB fallback was meant to rescue and could not, because the fallback still runs the same scorer. When the shorter normalized title is an exact whole-token PREFIX of the longer, the shared portion is a perfect match and only the dropped tail is uncertain, so `prefix_containment` scores it `0.9 + 0.1·(coverage)` and `title_similarity` returns the max of that and the Levenshtein. A minimum shared-prefix length (`MIN_PREFIX_MATCH_CHARS`) keeps a trivial leading word (`Code`, `24`) from blanket-matching an unrelated show — below it the whole-string Levenshtein still governs. The prefix must end on a token boundary (`forever` matches `forever us`, never `forevermore`), and the relation is symmetric so it fires whichever side carries the tail. Distinct from a genuinely unmatchable on-disk name: a season folder promoted to a series (`Season One`) or a raw release filename is a SCAN defect, not a scorer defect, and is out of this invariant's scope.
- V80: every segment of a shared-init fMP4 (CMAF) rendition must come from ONE encoder, because they all decode under a single init whose codec-private data is seg0's — and a parameter set, unlike a mux parameter, cannot be forced identical across two encoders. A CMAF media segment carries no inband SPS/PPS; the client configures its decoder from the init's `avcC` (seg0's SPS) and reads every later segment's slice headers against it. The scheduler load-balances each segment across NVENC and CPU by design (fine for the self-describing mpegts rungs, which repeat parameter sets per segment), so an h264 CMAF session could split across `h264_nvenc` and `libx264` — whose SPS differ in the slice-header determinants (POC type, `log2_max_frame_num`, ref structure) that `-profile`/`-level`/`-refs` do NOT cover — and a spilled segment is then decoded with the wrong SPS: `avcodec_send_packet: Invalid data`, the browser stalls. This is the parameter-set sibling of V78's timescale (which WAS a mux param and could be pinned). `device_supports` ORIGINALLY made hardware ineligible for `H264 + Container::Fmp4`, pinning the whole CMAF rendition — init and every segment — to libx264 (realtime at `-preset veryfast`, self-consistent, and it freed the GPU). Scoped to Fmp4: the mpegts h264 variants kept hardware under that scheme. Frame completeness (V67) and the timescale pin (V78) both pass on a segment whose SPS is wrong — neither reads the parameter set — so this is its own gate, verified by decoding a spilled segment under the rendition's init. Spec 003 R8 changed HOW the one-encoder guarantee is enforced, not whether: excluding hardware wholesale cost the entire GPU once all browser H264 became CMAF (420 of 423 jobs on the CPU with NVENC idle), so `device_supports` NOW keeps hardware ELIGIBLE instead, and the rendition resolves to exactly one device via `DeviceTable::rendition_device` — a pure function of the rendition key, so it survives a restart. Because eligibility is wide and only the pin narrows it, EVERY dispatch path must apply the pin: it is computed once in `candidates_for` and used by both `place` (arrival) and `try_place_no_queue` (drain). A path that rebuilds candidates from `eligible_for` alone will hand a queued CMAF job to whichever encoder's permit frees first. A pinned device in cooldown FAILS the request rather than spilling — on both paths — because a visible stall the client restarts from beats a segment no client can decode. Guard: scheduler.rs a_queued_cmaf_job_waits_for_its_pinned_device_rather_than_spilling.
- V81: the track the server SELECTS must ride the delivery URL, not only the DTO. V73 chooses the audio track a user starts on and reports it as `DefaultAudioStreamIndex`, so the UI shows it selected — but the demuxed audio rendition is a separate HLS session keyed by the `AudioStreamIndex` on its request, and that index reaches it only through the `TranscodingUrl` the server hands back. `stream_selection` forwarded only an index the CLIENT named on the request, and on first play jellyfin-web names none (it trusts the server's pick and appends `AudioStreamIndex` only after a manual switch), so `resolve_audio_rel` saw `None` and ffmpeg default-selected the container's first / default-disposition track: Aliens (three Ukrainian tracks ahead of its English DTS-HD MA) showed English selected yet played Ukrainian; Campfire (English default ahead of Japanese) showed Japanese yet played English. The selection was also computed AFTER the URL was built, so it structurally could not ride it. The server-selected absolute index (the one that becomes `DefaultAudioStreamIndex`) is therefore appended to the transcode URL when it carries none (`ensure_audio_index_param`, mirroring the `StartTimeTicks` append), idempotent with a client's later manual switch. A DTO field that says which track is selected is not the same as delivering it — the value that drives the render path must carry the choice too.
- V82: a capability field a client GATES a request on is answered from the same source that would serve the request. `MediaSource.HasSegments` is computed by `item_has_segments` from the detected segment rows plus the classifiable chapters — exactly what `/MediaSegments/{id}` returns — so the advertisement cannot promise what the endpoint lacks, nor hide what it holds. A hardcoded `false` on such a field is not a harmless stub: jellyfin-web returns before it ever calls `getItemSegments`, so the feature is unreachable with no failing request to find (B130). The verdict is recorded, because `false` is a decision and the field alone cannot distinguish "nothing to skip" from "never looked".

- V83: a search's DISCOVERY step and its ACCEPTANCE step use the same notion of similarity. Fingerprint alignment accepts two points at a Hamming distance of `max_bit_diff`, so its candidate shifts are enumerated over the overlap rather than seeded from exact-value equality — a pair of episodes sharing an entire opening within the acceptance tolerance must never fail for want of a numerically adjacent point (B131). Guards: a synthetic block whose points are all inside the bit tolerance and all outside any exact-value probe must still align, and the real-fingerprint fixture must locate the opening wherever it is present. Filler in a detector test is AVALANCHED, never stepped: an arithmetic ramp differs by a constant at every index and so aligns with itself under some shift, modelling an agreement real fingerprints cannot produce.


- V84: background work is throttled where its COST is, not where its cost used to be. `bg_io` regulates background *I/O*, and season consensus was left outside it because it had been cheap arithmetic over an indexed shift set. B131's exhaustive search moved the cost to CPU without moving the gate, and the work also ran inline on a tokio worker — so it could neither be parked by the regulator nor kept off the executor serving playback. Any background stage that becomes long-running holds a `bg_io` permit for its duration AND runs on `spawn_blocking`; a stage that does neither is invisible to the "stand down during playback" contract no matter what the adjacent stage does.

- V85: a consensus gate weighs evidence by its MAGNITUDE, not by its count. Season detection scored agreement as `agreeing / matched`, so three peers agreeing on a 109 s title sequence (0.43) lost to four short coincidental fragments, and every Game of Thrones S1 episode was discarded at 0.38-0.43 while adjacent seasons emitted the same span at 0.63-0.88. Counting votes treats an 18 s fragment and a full opening as equal testimony. Weight by matched seconds (T102); keep a separate `min_agreeing` count so one long coincidence still cannot carry an episode alone.

- V86: a derivation that REPLACES its own prior output snapshots it first, under a label, idempotently. `media_segments` is rewritten in place by a detector re-run, so the moment the sweep starts the evidence needed to judge it is gone — when SEGMENT_DETECT_VERSION 2->3 ran, "did recall drop?" was asked minutes later and was unanswerable. The snapshot must be taken before the first replacement and must never overwrite itself on a later pass, or it captures the post-change state and answers nothing (T103).

- V87: a search that rejects a candidate keeps looking among the rest. `compare` took only the LONGEST contiguous run at a shift and handed it to `bound_and_snap`; a run failing the duration bounds killed the entire shift, even when a shorter valid run sat at that same shift. Enumerate runs and take the first that clears the bounds on both sides (T104) — "best candidate" and "only candidate" are not the same thing.

- V88: when two readings of the same evidence fail in OPPOSITE directions, requiring both is a recall bug — take the better one and floor it separately. Season agreement was `agreeing/matched` (T102 showed a long true opening outnumbered by short coincidences: Game of Thrones S1 dropped entirely at 0.38-0.43), then `agreed_secs/located_secs` (T107 showed a short true ending outweighed by long spurious matches: Breaking Bad S5 credits 6 emitted -> 0, 78 outro rows lost library-wide). Each ratio is evidence, neither is the definition. The gate now clears on the greater of the two with `min_agreeing` as the independent floor. Corollary: a threshold change is not validated by the cases it was designed to fix — diff BOTH kinds against a pre-change snapshot (V86) before believing it.

- V89: when the RULE that assigns work to a device changes, every artefact cached under the old rule is stale — even if the artefact itself is still valid. Spec 003 moved CMAF H264 from "always CPU" to a deterministic device resolving to hardware, and research R8 argued no cache-generation bump was needed because a deterministic device means cached bytes always came from the device the rendition still resolves to. That holds only while the rule is FIXED; the deploy that introduces the rule is itself the moment it changes. Live consequence: 1489 CPU-era cache hits served alongside 11 fresh NVENC encodes for one episode, i.e. a libx264 init with hardware segments under it — the B-class #114 pairing failure, from disk rather than from the load balancer. Bump the generation whenever the assignment rule changes, not only when the device table does.

- V90: a response served `immutable` must have its identity IN THE URL. Anything the bytes depend on that is not in the URL becomes unfixable from the server: the stale copy lives in the client. `init.mp4` and `.m4s` are served `max-age=31536000, immutable` under URLs naming only item + segment index, so when the encoder assigned to CMAF changed, browsers paired an old init with new segments (B133/#114) and neither a server cache wipe nor a playback restart could clear it. Shared-init rendition URIs therefore carry `HLS_GEN_VERSION`. Corollary for diagnosis: when a fault survives a server-side cache invalidation, suspect the CLIENT cache before concluding the newly produced bytes are malformed — that inference cost a revert of a working feature.

- V91: whatever the miss path records, the hit path records too — a cache is not exempt from symmetry (V-class sibling of the rich-on-success/silent-on-failure shape). `segment_bytes_keyed` logged twelve fields on a miss (`transcode_ms`, `device`, `queue_wait_ms`, `frame_deficit`, …) and, on a hit, incremented one bare counter on its FAST branch and recorded NOTHING AT ALL on its post-lock re-check branch — so a segment served after queueing behind a concurrent mint of the same key appeared in neither the hit rate nor the miss rate. The consequence is not a missing nicety: the 2026-07-28 "Disclosure Day" investigation held 647 segment requests against 490 logged transcodes and could not say which of the remainder were cache hits, nor what had produced those bytes, so "was this session served stale output?" was unanswerable from the record. Both hit branches therefore emit `pharos_segment_cache_total{result,class,hit_path}` and an `hls segment served (cache hit)` line carrying the same identity fields as the miss line (`codec`, `burn`, `audio_idx`, `seek_secs`) plus `age_secs` and `read_ms`. `hit_path` is bounded to `fast` / `coalesced` and appears as `none` on a miss, because a label present on only one arm of a ratio silently drops series. (`post_lock` was renamed to `coalesced` in 006 phase 2a, when the per-key mutex became a shared-result registry: there is no lock to be "post" of any more, a later requester awaits the value instead of queueing for exclusion. The code cannot emit `post_lock`, so any panel or alert still selecting it is dead — this clause moved with the label rather than after it, because a contract that names a value the code cannot produce is the silent half of a rename.) The same symmetry binds the FAILURE half of the coalescing path: one failed encode returned to N waiters increments the production counter once, so each waiter also records `pharos_segment_produced_total{outcome="coalesced_failed", reason}`, as does a requester whose driver went away before `produce_segment` ran at all — panic or shutdown — since the encode that would have counted itself never started, and that holds for the requester that SPAWNED the driver too. `failed + coalesced_failed` is therefore the client-visible FAILURE total, and their ratio is the blast radius of a single bad encode. A shed inherited from an admission decision made about another job is deliberately NOT in that sum: it is client-visible, so it is counted, but as `outcome="coalesced_shed"`. The distinction is load-bearing rather than tidy — `failure_reason(SchedulerBusy)` is `"scheduler_busy"`, so folding these into the failure bucket puts deliberate load-shedding inside the sum this clause tells an operator to alert on, and under a prefetch storm (B108, the condition where Background work is shed BY DESIGN) `reason="scheduler_busy"` comes to dominate it: the alert then fires on admission control working. `shed + coalesced_shed` is the shedding total, the two sums are disjoint, and every outcome value is emitted from exactly one site so no arm can be counted twice. `age_secs` is the field that distinguishes a hit on this session's own prefetch from a hit on an entry old enough to predate a deploy — the V89/V90 question, which no signal could previously answer. The `class` on these two series is the SUBMITTER'S, and it is the opposite convention to the one the latency histograms beside them use — `pharos_transcode_encode_seconds{class}` is labelled by who was WAITING, so a promoted prefetch is timed `interactive` while its production is counted `background`. Neither is wrong and they must not be joined on `class`; see V128, where the split is spelled out.

- V92: speculative work is aimed at the request that will actually be made, and says where it aimed. The cold-start prewarm warmed segments `0..3` unconditionally while playback began wherever the viewer had resumed, so on a resume it was worse than doing nothing: three background encodes spent on bytes no client would fetch, AND the cold ffmpeg spawn the prewarm exists to absorb left sitting on the first request the client actually made (B136). A speculative stage therefore derives its target from the same position the response advertises (`start_position_ticks` / `StartTimeTicks`) and resolves it through the SAME `SegmentGrid` the playlist enumerates — deriving the index independently is how a warm segment and a requested segment drift apart. It also records what it chose and why, because a prewarm aimed at the wrong end of a title is indistinguishable at the metrics from one aimed correctly: both simply produce segments. Corollary: when a speculative stage cannot determine its target (no duration, position past the end) it declines rather than falling back to a default, since the default is precisely the case it is trying to stop being wrong about.

- V93: a control-plane WAIT states who it is waiting on and how it ended. A gate that logs only `pending=1` cannot answer "why is nothing happening?", and a gate rescued by a timeout that logs the same line as one every member acked makes a hang indistinguishable from health — B137 froze a group watch for ~37 s and had to be reconstructed from four Loki queries and three hand-correlated streams because both were true at once. So: every readiness gate names its holdout member ids at open, carries a reason label finer than the jellyfin wire string it broadcasts (five distinct situations all send `"Unpause"`, and they have different diagnoses), and terminates in exactly ONE recorded outcome — `resolved`, `anti_wedge`, `superseded`, `replaced` — which therefore sum to the number of gates opened, so a path that drops a gate shows up as arithmetic drift rather than as silence. The same holds for the V19 buffering freeze, whose only client-visible act is a bare `Pause` byte-identical to a user pressing pause: it records `recovered` / `superseded` / `anti_wedge` and how long it held, because "the group recovered" is not evidence of health when a human seeking out of the freeze is what ended it. Corollary, and the sharper half: an input the server DELIBERATELY discards is still an event. B137's viewer pressed play twice into an open gate; both presses were dropped correctly (replacing the gate would reset the anti-wedge deadline) and recorded nowhere, so the server's account showed a frozen group with no sign anyone had tried to resume it. A discard is a decision, and decisions are instrumented (ODD principle 2) — otherwise the most common user report there is, "I pressed the button and nothing happened", is unanswerable by construction.

- V94: a response that stops short of what the client asked for is only valid for a client that will ask again. Truncating a range is not a neutral optimisation — it is a statement about the media's length to any player that sizes its read from `Content-Length`, and a native progressive player believes it. Before capping, narrowing or otherwise shortening a body below the requested extent, name the client shape that re-requests the remainder; if it cannot be named, serve the whole extent. B140 truncated every Android TV DirectPlay to the first 8 MiB with a browser-shaped fix and reported three healthy 2xx responses while doing it.

- V95: artwork that pharos has downloaded is artwork pharos advertises. The `artwork` table mixes on-disk locators with bare remote URLs, and exactly one predicate decides which is which — `pharos_core::artwork_source_is_item_servable`. It is consulted by the sqlite and postgres `set_artwork` writers, which maintain the denormalised `has_primary_art`, and by the image route that resolves a role to a path; a new artwork source added to some of those and not others caches bytes that are never advertised and never served, with no error anywhere. One list, one home, asserted in a test that names every provider which downloads bytes (T108).

- V96: an endpoint a stock client calls by name exists, even when its data is empty. jellyfin-web issues many fetches with no rejection handler, so a missing route is not an error the user sees — it is a view that never finishes loading, and the report names the screen rather than the request. Before concluding a library is empty or broken, list what the client actually asked for and check every path resolves; `{namespace="pharos"} |= "status\":404"` is the query. B141 (`/MusicGenres`), the Edit Images spinner (`/Items/{id}/Images`) and the stuck audio switch (`DELETE /Videos/ActiveEncodings`) are the same bug three times.

- V97: a cached negative result records the logic version that produced it. Any sweep that stamps "we looked and found nothing" and then honours a TTL is asserting that the answer cannot change — but it changes every time the lookup improves, and the improvement then appears to do nothing for the whole TTL on exactly the items it fixes. Stamp the version alongside the verdict and invalidate on mismatch, the same discipline `PROBE_SCHEMA_VERSION`, `TRICKPLAY_GEN_VERSION`, `HLS_GEN_VERSION` and `SEGMENT_DETECT_VERSION` already apply to cached positive results. B143 is the negative-result case of the same rule.

- V98: a field a strict client dereferences unconditionally is set in the constructor, not at the call site. The kotlin SDK's DTOs are non-null; the Android TV app reads `item.userData.isFavorite()` with no guard, so an omitted `UserData` is a crash rather than a blank. Fixing that per-endpoint is how B68 was closed for library folders while every synthesised item kept the same hole for another year. When a client-required field is discovered, set it in the shared constructor and assert it across every surface that constructor feeds — the assertion over ALL surfaces is what proves the fix is structural (B146).

- V99: a cached failure remembers WHY it failed. Memoising a miss as a bare absence makes every repeat report a stand-in cause, and since repeats vastly outnumber first attempts, the aggregate signal then describes a problem nobody has. B147 read 192 `no_candidates` against 26 `below_confidence` when nearly every miss was below-confidence, and the ratio pointed at the query for two rounds of fixes while the real fault was in scoring. Store the reason, not just the failure, wherever a per-item verdict is cached and counted.

- V100: relaxing a query removes a constraint, so the constraint has to be re-applied when the result is judged. Each rung of a search ladder that drops a term widens what can come back, and scoring that ignores the dropped term cannot tell the widened results apart — B150 dropped the artist from the query AND from the score, and 217 albums called `Fireflies` became indistinguishable perfect matches. Whatever a rung drops, the acceptance test must check. Corollary: a cached result is only as trustworthy as the matcher that produced it, so record the matcher's version alongside it and invalidate on a bump — a wrong answer that already looks answered is invisible to every later pass.

- V101: a filter that names something unknown narrows to nothing, never widens to everything. Parsing a client's filter into "the values we recognised" loses the difference between "no filter asked for" and "a filter we cannot satisfy", and defaulting the second to the first turns a precise request into a whole-library scan — B153 answered a request for music videos with 51.6 MB of films and episodes. Represent the empty-after-parse case explicitly and decide it deliberately; where a named value is one the server answers by synthesis rather than storage, say so in a list that can be read, not by accident of a parser returning nothing.
- V102: a group's poster comes from a member that HAS one. When an aggregate item (album, artist, series, library) picks a representative member to stand in for its image, membership in "has art" ranks ahead of every cosmetic ordering key. Ordering by title/number alone silently picks a blank member out of a group that is not blank, and the wire shape is indistinguishable from a group with no art at all (B154).
- V103: a cache whose correct answer depends on data a background job is still writing must be invalidated by that job, not by restart. Memoised derivations of mutable state (the synth-image representative map) carry an epoch the writer bumps; a reader that finds a moved epoch rebuilds. "It fixes itself on the next deploy" is the signature of this class (B155).
- V104: every id an endpoint HANDS OUT must resolve when handed back. A list builder that emits a synthesised id creates a client navigation target; the item-detail fetch has to resolve that id shape or the surface dead-ends. New synth id shape → a resolution arm in `fetch_item_dto`, in the same change (B156).
- V105: fetch the size you are going to render. When a provider publishes derived sizes, request the derivative that covers the largest surface that displays the asset — never the original. And a network client gets a connect timeout separate from its whole-request timeout, so "host is down" and "transfer is slow" stay distinguishable (B158).
- V106: a decision with several rejection grounds must report the one that actually fired, and the value it fired on. Reusing a neighbouring metric for the message produces reasons that contradict the verdict and send the reader to tune an uninvolved threshold — strictly worse than saying nothing. Corollary for the TEST: assert the SELECTION of the reason, not its formatting; a test that hand-builds the variant and checks its `Display` passes with the routing disarmed (B159).
- V107: invalidation is priced by what it destroys, so a cheap trigger must not fire an expensive one. Separate "re-examine what FAILED" (free — re-admit the rows that recorded a failure) from "discard what SUCCEEDED" (expensive — re-fetches everything from a rate-limited provider), and gate them on different versions; bump the destructive one only when a past success may be wrong. And an ABSENT version record is not a stale one — adopt it silently, or every fresh install pays a full rebuild on first boot (B160).
- V108: a payload that exists to be MEASURED must be incompressible, and must say so. Anything whose size is the point — throughput probes above all — has to resist every layer that might helpfully shrink it, both by construction (high-entropy content) and by declaration (`Content-Encoding: identity`). Filling such a body with a cheap constant makes the measurement a function of the compressor rather than the link (B161).
- V109: compress at the layer that only sees text. Response compression belongs where it can be scoped to text-shaped content types by an allow-list, not on a path that also carries media: a compressor that switches a video or image response to chunked transfer breaks the `Content-Length`/`Range` contract those paths depend on. Byte-exact payloads (throughput probes) stay outside the allow-list (B162).
- V110: decide on the property you actually care about, not a proxy for it. Scaling an image is a question about its DIMENSIONS; file size only correlates, and the correlation breaks exactly where it matters (a well-compressed full-resolution photograph). When the true property is cheap to read — an image header is a short read, not a decode — read it (B163).

- V111: a list endpoint honours the size the caller asked for. `Limit`/`StartIndex` are part of the request, not a hint — an endpoint that ignores them looks correct (the client renders the first N and drops the rest) while moving the entire table on every page load, so the defect is invisible except as bytes. `TotalRecordCount` stays the unpaged total (B164).

- V112: a reverse proxy forwards the CLIENT's context, it does not substitute its own. `X-Forwarded-*` headers exist to carry what the origin cannot otherwise see; setting them from the proxy's own connection (`$scheme`, its own address) destroys exactly the information they exist to convey, and the damage surfaces far away — as a plaintext URL the server advertises about itself. Honour an inbound value, fall back to the local one only when there is nothing in front (B165).

- V113: a HEAD advertises exactly what the GET would send. The response must DECLARE the real body size — in actix that means a sized body, since the encoder derives `Content-Length` from `BodySize` and discards a hand-set header — while never reading the bytes. Clients size a fetch from HEAD, so a zero reads as "nothing there" (B101, B166).

- V114: membership is never revoked by a timer while the group is alive. A member that cannot be heard from is not thereby known to be gone — a client reconnecting and a client that closed its tab produce identical evidence, namely silence — so no duration distinguishes them and each attempt to pick one has been exceeded in the same direction (150 s, then 600 s, against real reconnects of 12–22 minutes). Where a member's absence blocks nothing (it holds no readiness gate), retain it; decide abandonment for the GROUP, where the evidence is unambiguous — nobody connected and nothing heard — and dissolve it whole. A roster is never quietly thinned. Corollary: liveness inferred from ACTIVITY punishes the passive participant, so the quiet majority is evicted first (B167).

- V115: whatever the success path tells the client, the failure path tells it too. A reconnect that finds a membership sends a full re-join; a reconnect that finds none must say so rather than log to nobody — a client that is not told keeps rendering the state it last knew, and the divergence is invisible on both sides until a user happens to interact. When the correcting message is user-visible (jellyfin-web toasts on `disableSyncPlay`), send it only where the server holds actual evidence of the contradiction, never as a blanket assertion on every connect (B168).

- V116: a timestamp means what its source says it means, not what it resembles. A container's `creation_time` records when the FILE was written; a release date records when the WORK came out. They have the same shape and are never the same fact, so one must never stand in for the other — the substitution is invisible on new files (where the two nearly agree) and wrong by decades on everything else. Corollary for merges: when several sources can supply a field on a first-wins rule, record WHICH one won, or a value from the wrong source is indistinguishable from a value from the right one (B169).

- V117: a field a client GATES on is not a field a client asks for. `Fields` is an optimisation for payload size; it cannot be the mechanism that decides whether a feature works, because the request that decides is often the one that asks for nothing. jellyfin-web's item-detail fetch sends NO `Fields` and hands the result straight to `playbackManager`, whose readers all test `item.Path` — so gating `Path` on `Fields` made every book unopenable with no error, no toast and no network request (B170). Where a field is load-bearing for a kind, emit it for that kind unconditionally and keep the gate for the kinds where it is merely detail. The converse still holds and is not weakened: a path is never SYNTHESISED to satisfy a client-side extension test, because what is served must be what exists.

- V118: adding a variant to a domain enum obliges you to audit the sites the compiler will not show you. `rustc` enforces exhaustiveness only for a `match` with no wildcard arm; a `matches!`, an `==`, a `!matches!` and a wildcard-armed `match` all compile silently against the new variant and silently give it the old answer. Adding `MediaKind::Book` found 44 such sites, one of which — `_ => "Video"` deciding `MediaType` — would have failed the entire feature with nothing to read anywhere. Audit BEFORE the variant exists, which is the only window in which the sites are enumerable, and record the verdicts; where a site is load-bearing, convert it to an exhaustive `match` so the NEXT variant cannot compile until it decides. Worked example: `specs/004-books/kind-decision-audit.md`.

- V119: a third-party parser handling user-supplied files runs behind a panic guard. A crate can promise memory safety (`forbid(unsafe_code)`) and bounded recursion and still panic — lopdf alone carries 173 `unwrap()`s — and a panic that escapes a scan kills the whole RUN, so one hostile file stops every later file being indexed: a large invisible failure caused by a small visible one, which is precisely what V6 forbids. Catch it, record it under its own reason (a panic is the parser failing to report, NOT the parser reporting a bad file), name the offending file, and still import the item. This does not cover an abort or a stack overflow — nothing in-process can — which is why the parser's own depth bound is load-bearing rather than something a guard can paper over (B173).

- V120: when containers nest, the most specific one owns the thing. Assignment by "iterate and let the last writer win" is only correct if the iteration order encodes specificity, and an order chosen for DISPLAY (alphabetical) does not — it makes correctness depend on what someone named a library. Sort by specificity at the point of assignment, keep the display order where it belongs, and assert the case where the nested container's name sorts BEFORE its parent, because that is the arrangement that fails (B174). Corollary: a comment asserting that some configuration "doesn't happen in practice" is a prediction, not a constraint; the first person to configure it that way gets silence rather than an error.

- V121: a format the CLIENT cannot open is not the same fact as a format PHAROS cannot read, and the stored format must answer the first. When a file is converted before delivery, `book_format` records what a client can read it AS (epub) while the path keeps recording what the file on disk IS (`.azw3`); the two disagreeing is what identifies a converted item, so no flag can drift out of step with the values it would summarise. Corollary: disk stays the authority on whether converted bytes exist — advertise from the row, regenerate on a miss, and a wiped cache costs one rebuild rather than a broken link (005-kindle-conversion).

- V122: a permanent property of a file is not a failure, and must not be counted as one. DRM-protected books have no fix in code; folding them into a generic `failed` bucket makes 58 of a 75-file shelf read as a bug and sends the next reader hunting for a parser defect that does not exist. Give the unfixable outcome its own label, log it at debug rather than warn, and keep the fixable failures loud beside it.

- V123: an ignored security advisory needs a reachability ARGUMENT naming the code path, not an assertion that it does not apply. Two advisories against the same pinned crate can be unreachable for entirely different reasons — one because the vulnerable type is never constructed, the other because the vulnerable module is never entered on the paths this project uses — and only the second survives a change in which formats get handed to the dependency. Record which, so the next person can tell whether their change invalidated it (005-kindle-conversion, quick-xml 0.39 via boko).

- V124: a client we SHIP is part of the product, and its cost is ours to measure and to fix. pharos serves jellyfin-web from its own image, so "the slowness is upstream's" describes where the code lives, not whose problem it is: an 8 ms server response behind a 35 s reader is a 35 s feature. Where a vendored bundle's defect is a constant rather than a design, patch it in the derivation that builds the image — and make the patch FAIL THE BUILD when it stops matching, because a minifier-chosen identifier can be renamed by a dependency bump and a silently-no-op patch restores the original slowness while every test still passes. Assert the patched value in the served bundle too: the build check proves the rewrite happened, only a check on what is served proves the right bundle is wired in (B175, epub.js `Locations.pause`).

- V125: a reserved permit is not reserved throughput. Admission control that keeps a slot free for latency-critical work only guarantees that work can START; on a shared device — one GPU, one encoder, one disk — what it needs is a share of the device while it runs, and speculative work admitted beside it takes that share. Reserve capacity AND bound how much optional work may run alongside the request someone is blocked on. The bound must not be zero: where the optional work is shed, refusing it entirely means it is never retried and the cache it exists to fill stays cold; where it is deferred instead (V58), a zero bound starves it just as completely, because a job refused on every device is a job that is never selected. Either way the device that has earned nothing still runs one (B177, transcode prefetch vs client segments).

- V126: a performance tunable that must know the hardware is a defect. A constant that has to be recalibrated per machine is a constant that is wrong on every machine but the one it was measured on. Where a limit exists to protect a client-visible deadline, express the DEADLINE and learn the limit from observed outcomes on the device in front of you. Concretely: speculative transcode concurrency is learned per device by `pharos_transcode::admission`, from whether the segments clients actually waited for made a deadline set as a fraction of their own playback duration. The configured value survives only as the floor, and the replacement constants (`margin_ratio`, `increase_step`, `decrease_factor`) are dimensionless — response shape, not machine capability — or the problem has only moved (006, B177, V125).

- V127: an outcome computed for ONE job's parameters must not be adopted as another job's answer. Sharing a RESULT between requesters is the point of single-flight and is always right — the bytes of a segment do not depend on who asked for them. Sharing a POLICY DECISION is never right, because the decision was made about the submitter: its class, its priority, the capacity that existed at its moment. B134's shape was a client request coalescing onto a speculative prefetch and inheriting that prefetch's `SchedulerBusy` — a correct answer to "should this guess run?" returned as a 500 on a video segment somebody was watching, and load-correlated, since Background is shed precisely when an Interactive request most needs admitting. The rule is stateless and class-blind: a requester that did not submit the job declines the job's admission verdict and drives its own, ONCE (a bounded fall-through, never a retry loop — a requester that resubmits until admitted is running its own unbounded queue outside the scheduler, which is the one place that can rank the work; and a requester that submitted its own job keeps its own shed). The accounting obeys the same split: a shed reaching a client is counted as a shed and not as an encode failure (V91), or the conflation simply moves from the response to the dashboard. Corollary for the next author: this shape lives wherever one computation answers several requesters, and pharos has three more such sites today — `pharos-cache::single_flight::KeyedLocks` (behind `ImageCache`), `subtitle_cache.rs` and `trickplay_cache.rs`. Each is safe only for as long as what it shares is a result; the day any of them shares an admission verdict, a rate-limit refusal, a deadline or a cancellation, it has this bug. Audit for "would this answer have been different had the LATER requester asked first?" — if yes, it is a decision and it is not shareable. The verdict is not the only such decision: a job's PRIORITY is one too. Since V58 lets speculative work wait for a permit, a client coalescing onto a prefetch would inherit its tier and wait behind every other client's work, including work submitted after it started waiting — the same hazard as the inherited shed, arriving as a delay instead of a 500. The answer is the same shape: the joiner declines the driver's class and has the job promoted to its own.

- V128: the arms of one counter must count the same kind of thing, and be recorded at a TERMINAL decision rather than at an examination. A counter whose arms have different denominators is worse than no counter: its absolute values look reasonable, its ratios are meaningless, and nothing in the dashboard says so. Two instances on this branch, both in the transcode scheduler, both because a queued job is RE-EXAMINED on every drain pass while the pool stays busy: `pharos_transcode_pin_total{outcome="followed"}` was incremented inside `candidates_for` and so counted examinations while `{outcome="invalidated"}` counted jobs, inflating unboundedly under saturation — exactly when the metric is read to verify the pin; and `pharos_transcode_queue_outcome_total` would have repeated it had `dispatched` been recorded where a job is looked at instead of where it takes a permit (its disarm reads 4 for one job). The rule: pick the moment the subject STOPS being the counter's business, record there, and record once. Where a subject can legitimately pass that point twice — a job re-placed after a transient device failure — count the first pass only, and say in the code which flag makes that true (`retries == 0`, because the only route to a re-placement is a dispatch). The arms must also PARTITION their subject: `pharos_transcode_queue_outcome_total`'s six (`dispatched`/`stale`/`evicted`/`shed`/`abandoned`/`failed`) exist because six is how many ways a job can leave the queue, so their sum is submissions and any one over the sum is a real fraction. Naming fewer arms than there are exits does not remove the exits, it hides them inside whichever arm is nearest — a job whose caller went away or that no device can encode, folded into `shed`, reports load management that never happened. A label whose VALUE can change during the subject's life is a third way to get different denominators, and it must be written down where the metric is defined rather than discovered from a dashboard: `pharos_transcode_queue_outcome_total`'s `class` is mutated in place by promotion, so `sum(...{class="background"})` is background submissions MINUS promotions, and `pharos_transcode_queue_distance` — which a promoted job never reaches, being `Interactive` by dispatch — describes the guesses NOBODY joined. That is the right shape for "is prefetch depth tuned too far ahead" and the wrong number for "how deep speculation runs", and no label could expose it. A label whose NAME is shared by two counters answering different questions is the same trap wearing the opposite clothes, and it has to be written down here for the same reason — nothing in a dashboard says so, and both families are about segments, so an operator will instinctively join them. `pharos_transcode_encode_seconds{class}` and `pharos_transcode_queue_wait_seconds{class}` are labelled by WHO WAS WAITING: a speculative encode a client coalesced onto is timed as `interactive`, because it IS a client-blocking encode and filing it as background understates the interactive p95 the control law is validated from (42% of interactive cache hits arrive coalesced), and the scheduler's own `observe_margin` already treats a promoted job as interactive, so the two must not disagree about one job. `pharos_segment_produced_total{class}` and `pharos_segment_cache_total{class}` are labelled by WHO SUBMITTED: they count production attempts and requests, they describe the driver, and a joiner already counted its own request on the coalesced-hit path. So over any interval containing promotions, `produced_total{class="background"}` counts encodes that `encode_seconds{class="background"}` deliberately does not time, and a ratio of the two is not a fraction of anything. Guards: scheduler.rs a_pinned_job_examined_across_several_drains_records_followed_once, a_queued_job_is_counted_once_however_many_drains_examine_it, queue_outcome_labels_are_distinct_and_stable, the_partition_covers_abandonment_failure_and_a_shed_with_no_victim; hls_cache.rs a_client_blocking_encode_is_timed_as_interactive_however_it_started.

- V129: a cache generation that gates an `immutable` response is DERIVED from the rule that decides the bytes, never hand-maintained beside it. V89 says bump the generation when the assignment rule changes and V90 says put it in the URL; both assume a human notices the change. Spec 007 broke that assumption without moving either invariant: `rendition_device` bands renditions by device WEIGHT, the weight is `capacity x a bucketed speed ratio`, and `probe_device_caps` ramps trial encodes until one fails — its own module documenting that "probing a box already under encode load under-reports". So an ordinary restart during playback can measure capacity 3 where the previous boot measured 4, move every band, and re-place every rendition whose key position falls between the two grids, with `HLS_GEN_VERSION` sitting still: cached `.m4s` from the previous encoder on disk, and — beyond any server-side wipe — an `init.mp4?…&g=16` the browser holds `immutable` for a year. #114 on a restart, delivered with a 200, with no deploy and no hardware change to point at. The generation is therefore composed as `HLS_GEN_VERSION` + `DeviceTable::placement_fingerprint()` (`pharos_cache::compose_generation`), installed once at boot before the cache reconciles or any playlist is rendered, and read through `pharos_cache::generation()` by BOTH the on-disk marker and the `g=` in every shared-init URI — a wipe without a URL change leaves the browser's init in place, a URL change without a wipe leaves stale bytes on disk. The digest holds exactly the `(device id, weight)` pairs placement reads, sorted: cooldown and in-flight load are excluded because a transient `DeviceBusy` must not wipe a 40 GiB cache, and enumeration order because it is a scheduling preference rather than a hardware fact. Corollary: persisting the probe (`rate_store`, V130) is a boot-time optimisation, not the correctness mechanism — it makes the common drift stop happening, but a device the boot probe cannot confirm at all still changes the device set and still re-places. Guards: device.rs placement_fingerprint_tests (identical_weights_hash_identically, a_capacity_drift_of_one_changes_the_digest, changing_the_device_set_changes_the_digest, the_device_order_does_not_change_the_digest, transient_state_stays_out_of_the_digest); hls_cache.rs generation_tests (a_drifted_placement_digest_composes_a_different_generation, reconcile_wipes_on_a_generation_change_and_keeps_it_otherwise, the_wipe_spares_the_persisted_rate_store, installing_a_digest_fixes_the_generation_for_both_readers); hls.rs a_shared_init_rendition_uri_carries_the_cache_generation.

- V130: a placement input derived from a MEASUREMENT is reconciled against its persisted value, never re-derived from scratch. V129 makes a moved weight self-invalidating, which is what stops the corruption; it does not stop the move, and the move costs a 40 GiB segment cache and every client's `immutable` init. Both factors of the weight are measured and both drift without any hardware changing: the encode rate varies run to run, and `probe_device_caps` ramps concurrent trial encodes until a level fails, its own module documenting that "probing a box already under encode load under-reports" — while the chart runs it on every pod start, so a restart during playback measures a smaller capacity than the boot before it. `rate_store` therefore persists the WHOLE probe result beside the transcode cache and `main.rs` resolves the boot probe through it. Its fingerprint keys on the device SET IDENTITY — ids alone — because keying on capacity was self-defeating: the drift the store exists to absorb was a capacity drift, and it invalidated the store meant to absorb it. On a matching fingerprint the rates are reused verbatim and NO probe runs, so a rate cannot differ between two boots at all; a MEASURED capacity is reconciled by a RATCHET, `max(stored, probed)`, which is sound rather than optimistic because `probe_caps` returns the highest concurrency at which every simultaneous encode SUCCEEDED — a demonstrated lower bound, so the maximum over boots converges upward to the truth, absorbs a loaded boot's under-reading, and still recovers from a first boot that was itself under load (plain reuse would freeze that forever). The ratchet applies to what a NOISY RAMP measured and to nothing else: every argument for it is an argument about measurement noise, and applying it to a number with no noise term silently overrides the operator. Two of the capacities the store is handed are exactly that — `default_cpu_permits()` is `available_parallelism() / sw_encode_threads()`, so a 16-vCPU node down-sized to 8 would keep 4 permits and over-subscribe software encoding 2x permanently while nothing surfaced it (a software encode is never REFUSED, so the cooldown that makes a hardware over-subscription visible is never entered); and with `transcode_probe_caps = false` every device's capacity IS `transcode_hw_session_cap`, so lowering it from 8 to 2 to throttle a GPU would be ignored for the life of the deployment. `rate_store::CapacitySource` therefore carries the provenance per row, set by the caller that produced the number, and a `Declared` capacity is taken at face value in both directions — it moves the weight when it falls, and the boot log says so without attributing the change to a measurement artefact. Two costs remain, accepted rather than hidden and recoverable only by deleting the file whose path is logged at boot: a MEASURED device whose true capacity genuinely FALLS is over-subscribed, and a persisted `None` rate is permanent — it weighs its device on capacity alone AND drops that device out of the reference minimum, holding down every other device's weight. Neither is graceful: under V128's pin rule `candidates_for` records `Invalidated` and FAILS a shared-init rendition whose pinned device is in cooldown rather than spilling it to a second encoder, so a permanently over-subscribed device fails its banded segments on every cooldown cycle, viewer-visibly and indefinitely. Both conditions are states that outlive a boot log, so both are published as gauges — `pharos_transcode_device_rate_unmeasured{device}` and `pharos_transcode_device_capacity_suppressed{device}` (the number of sessions the ratchet is withholding, so `> 0` is "suppressed now" and `min_over_time` over a month distinguishes one loaded boot from a capacity that really fell) — with an explicit 0 for the healthy case so each can be read as a rate, on every path including the one with no store to persist to. Both are set once at boot and never refreshed, which is sound only because the Prometheus recorder carries no `idle_timeout`; adding one would silently delete them. Guards: rate_store.rs a_matching_fingerprint_reuses_stored_rates_without_probing, a_boot_under_load_measuring_less_capacity_keeps_the_stored_one, a_larger_measurement_ratchets_up_and_persists, a_changed_device_set_reprobes_but_a_resize_does_not, a_declared_capacity_falls_while_a_measured_one_in_the_same_table_holds, lowering_a_configured_session_cap_is_not_ignored, an_unmeasured_device_is_visible_as_a_gauge_including_when_reused, a_suppressed_capacity_is_visible_as_a_gauge.

- V131: a decision whose input nobody can see must publish both. Placement is now spread across every supporting device by a probe-derived weight, so a rendition landing somewhere surprising has two indistinguishable explanations — the weighting was wrong, or the placement did not follow it — and on hardware nobody has tested that is the first question anyone asks. `pharos_transcode_device_weight{device}` is the share a device was GIVEN and `pharos_transcode_rendition_pin_total{device}` is the share it GOT; either alone answers neither question. The weight is published beside `pharos_transcode_device_capacity` and is deliberately NOT it — capacity is one factor of the weight, so a dashboard carrying only capacity looks correct while a mis-weighting goes unnoticed, and both guards weigh something other than the permit count so that reporting capacity under a new name fails. The pin counter is recorded at the dispatch point per V128, never inside `candidates_for`, which runs on every examination of a queued job. Guards: scheduler.rs a_followed_pin_is_counted_against_the_device_it_resolved_to, a_pinned_job_examined_across_several_drains_records_followed_once, snapshot_reports_the_placement_weight_not_the_capacity; router.rs the_device_weight_is_published_and_is_not_the_capacity.

- V137: a job may offload its SOURCE DECODE to a device only for a (source codec, device) pair a real trial decode proved, and an unproven pair decodes in software. Naming a decoder is not having one, and the difference is not a per-family constant: NVDEC's AV1 support arrived mid-generation, so "NVENC" is not the unit the answer varies on and a hand-written table would be exactly the hardware-specific constant V126 forbids. `probe_decodable_codecs` therefore trials each `SourceCodec` per device at boot — a software-encoded five-frame sample, then a decode of it through the device's own `-hwaccel` flags, `-hwaccel_device` included so a multi-GPU box probes the card it will encode on — and a codec whose SAMPLE fails to build is skipped rather than reported undecodable, because the probe failing to build its own input says nothing about the card. `DeviceSlot::decodable` is `Option` and the `None`/`Some(empty)` distinction may not be collapsed: `None` is "never probed" and keeps the pre-probe behaviour for callers with no measurement, `Some(empty)` is a real answer that must be believed, and collapsing them reinstates the defect. The verdict is taken ONCE, at dispatch, because the device is not known until placement, and travels on `JobSpec::decode_offload` because the argv is built in a separate PROCESS that holds no capability table — deriving it at argv time from the device alone is precisely B179. Denying it moves only the DECODE to software; the encoder stays where the scheduler put it, which is what makes the gate cheap enough to apply whenever the answer is unproven. An unnamed source codec is denied: the two ways of being wrong cost a dead rendition and a slower encode respectively. Corollary: a scheduling input like this must not reach `RenditionKey`, which digests `TranscodeOptions` through serde — clearing the field is not enough, serde still emits the key and the pin still moves, so it is excluded at the declaration with `#[serde(skip)]`. Guards: device.rs a_probed_device_offloads_only_the_codecs_its_trial_decode_named, an_empty_probe_result_is_not_the_same_as_never_probing, decode_capability_does_not_move_the_placement_fingerprint; probe.rs the_decode_trial_uses_the_same_hwaccel_flags_production_emits, every_probed_codec_can_have_a_sample_built_for_it, the_cpu_has_no_decodable_set; lib.rs a_denied_decode_offload_emits_no_hwaccel_but_keeps_the_hardware_encoder; scheduler.rs a_source_the_device_cannot_decode_is_dispatched_without_hardware_decode; options.rs only_fields_that_distinguish_renditions_move_the_key.

- V138: a failure is classified by WHAT failed, never by WHERE it ran, and only a failure that is evidence about the DEVICE may take that device out of service. `classify_failure` decided on one bit — hardware or not — so every non-source failure on a GPU became `DeviceBusy`, the only transient class and the only one that cools. Under V128's pin a cooled device does not slow a rendition, it fails it, so on 2026-08-01 a single file a Pascal card could not decode cost 453 client segments of unrelated titles (B180). A decode failure is the opposite verdict about the same hardware: it says this SOURCE and this DECODER cannot work together and says nothing about the card, which encodes fine either side of it. `WorkerError::DecodeFailed` carries it, is not transient (the offload decision is made per (source, device) BEFORE dispatch, so an identical retry elsewhere fails identically), and is matched on strings that name the decode side explicitly — `Decode error rate N exceeds maximum M`, `hwaccel initialisation returned error` — checked before the hardware arm so the lift cannot swallow a genuine device fault. Corollary, and the reason this is one invariant rather than two: narrowing what cools a device silently narrows the only instrumentation a failed job had. `pharos_transcode_job_failed_total{device,reason}` is therefore part of the same rule — a rendition that fails every segment forever must move a series, not just a log line. Guards: exec.rs a_decode_failure_does_not_take_the_device_out_of_service, a_failed_hwaccel_decoder_setup_is_a_decode_failure_not_a_device_fault, a_real_device_fault_is_still_transient; scheduler.rs a_non_recoverable_failure_is_counted_against_its_device_with_a_reason, cooling_a_device_is_counted_against_that_device_with_a_reason.

- V132: a cached artefact is invalidated everywhere it was published, or not at all. The segment cache is not the only cache: segments and init ship `Cache-Control: public, max-age=31536000, immutable`, so bytes that change behind a stable id survive in the BROWSER for a year, out of reach of any server-side wipe. A URL-backed source's bytes move whenever the resolver returns something new, so a per-item `SourceGen` derived from the locator must appear in EVERY published surface: `SegmentIdentity` (the server's disk key), the segment `ETag`, and the query string of every URI whose response is served `immutable` — a wipe without a URL change leaves the browser's copy, a URL change without a wipe leaves stale bytes on disk. It CANNOT ride `pharos_cache::generation()`: that is a process-wide `OnceLock` fixed at boot, and bumping it because one remote video re-resolved would wipe every local title's segments. 007's `g=` answers "did the SERVER's placement rule change", a per-process question; this answers "did the bytes behind this id change", a per-item one, and neither substitutes for the other. The trap is on both sides and the query-string rule therefore lives in ONE place (`with_source_gen`): omit `s=` and an `immutable` response outlives the bytes it describes, apply it unconditionally and every LOCAL item's URLs change, busting a warm cache and every held init for an item whose bytes cannot move. "Every published surface" is meant literally and was got wrong once already — the mpegts rung is exempt from the `#114` shared-init hazard `g=` exists for, so it never adopted `rendition_qs`, but `serve_segment` hands its `.ts` files back `immutable` exactly like every other segment and it needs `s=` regardless (B181). The subtitle/waveform keys are NOT in this set: see V133, withdrawn, because those keys already carry an identity of their own. Guards: hls_cache.rs a_re_resolved_source_gets_a_different_key_and_etag; hls.rs a_shared_init_rendition_uri_carries_the_cache_generation; remote_end_to_end.rs a_url_becomes_an_item_a_client_can_play.

- V134: a background sweep that cannot succeed on an item must DECLINE it, not retry it. `ensure_generated_all` fails on an unknown protocol, so `is_generated` never becomes true and the item is retried every `PASS_INTERVAL` forever, holding a `BgPermit` each pass — the permit the regulator parks during playback. The same shape sat in the trickplay, segment and metadata backfills, and the fingerprint path additionally does `File::open` → ENOENT. This is a SHIP-ORDER dependency rather than a tidy-up: the decline must land before any commit can insert a remote row, or the first insert starts an unbounded retry loop competing with playback for the background-I/O gate. Generalised, it is the same rule the probe memo enforces one layer down (see B-series, `probe_memo`): a failure with no record is retried forever. The decline is expressed through `Origin`/`LocalPath` rather than a path-prefix test, so a sweep that forgets the branch does not compile — the risk is not on the playback path, which gets inspected, but in a sweep that takes a `&Path` out of a struct field and where nobody thinks to add one. Guards: trickplay_backfill.rs the_sweep_declines_a_remote_item_and_still_takes_a_local_one; metadata_backfill.rs a_remote_item_searches_by_title_not_by_its_synthetic_path, detection_declines_a_remote_episode_and_still_takes_a_local_one.

- V135: a network fetch does not spend the disk budget. `bg_io`'s whole design is that minting a permit forces a choice between competing for disk and being unmetered, and "network" is a third answer it could not express. Taking `BgPermit::acquire` for an upstream fetch occupies a gate it does not contend for — throttling scans and warming against I/O that never touches the disk — while marking it `playback_priority` leaves a background prefetch entirely unmetered against a link that IS shared. `NetworkGate` is a distinct TYPE and not a second constructor on the same one: two constructors with identical signatures separated only by doc comments enforce nothing, and the whole point is that the choice cannot be made by accident. Guards: bg_io.rs a_network_fetch_meters_on_its_own_gate_not_the_disk_one, a_zero_width_network_gate_is_clamped_rather_than_deadlocking.

- V136: a synthetic item is never parked under a directory a scan walks. `sweep_unseen` is safe for URL-backed rows only by an accident of arithmetic: a walk of a nonexistent root yields a walkdir error, `walk_errors == 1`, and the sweep is skipped. Park them under a REAL scan root instead and the walk succeeds, finds none of them, and deletes every remote row. B98's blast-radius guard does not save it — that needs >=100 deletions AND >25%, so a library of 40 videos is wiped without so much as a warning line. - V139: a coordination wait must never depend on an acknowledgement the waited-on party has no way to produce. jellyfin-web posts `Ready` only on a player TRANSITION, so a member already in the state a wait is waiting FOR emits nothing at all — it is not slow, it is mute, and no amount of patience converts silence into an answer. Three separate defects in one evening were this one rule unlearned: a seek gate sized for loading an item, held on members whose player was already at the target (B182); a group seeded but never broadcast, so no client held the queue entry a `Ready` would have to echo (B183); and a buffering freeze superseded by the very member still buffering, whose re-report then re-froze it three seconds later (B184). B137 had already named the shape — "waiting 30s on a member that has no way to answer is not patience, it is a hang" — and bounded exactly one of its instances. Concretely, every wait must satisfy three tests before it is added: (1) name the transition the waited-on member will make, and if there is none the wait is unsatisfiable by construction; (2) bound it by what that transition COSTS, so a wait for an item to load may be long and a wait within an already-loaded item may not; (3) make the give-up path a normal outcome that is counted, not an emergency — `outcome="anti_wedge"` running at 5 of 9 is a design defect reporting itself, and was the only reason B182 was findable at all. Corollary, from B184: a mechanism that keeps a wait safe by RE-REPORTING is only safe if the re-report is rate-limited; an unconditional re-report converts a hang into a loop, which is worse, because a hang is visible as a bug and a loop looks like bad video. Guards: group.rs a_seek_gate_gives_up_long_before_the_new_item_timeout, a_joiner_promotes_a_seed_only_queue_so_every_member_is_bound, an_unpause_breaks_a_buffering_freeze_once_but_not_on_a_loop, buffering_freeze_times_out_via_anti_wedge.


- V140: a media file is not known to be playable until something has read it end to end, and the thing that reads it must count what libav SAYS, not only what libav RETURNS. Every check pharos had stopped at the header: `avformat_open_input` answers codec, resolution and duration, and a file whose header is intact but whose body carries a hole of null bytes answers all three correctly. It enters the library indistinguishable from a healthy one and the damage is discovered by a viewer mid-episode (B185). The check that closes this demuxes the whole file and decodes nothing — the in-process form of `ffmpeg -v error -i FILE -c copy -f null -` — and it must attend to three separate failure shapes, because each is silent in the others' terms. (1) Errors libav returns: a non-EOF `av_read_frame` failure, or `AV_PKT_FLAG_CORRUPT`. (2) Errors libav only LOGS: the matroska demuxer resyncs past a hole internally, so no call fails, no packet is flagged, and the scan reaches EOF reporting success while the CLI on the same file prints `invalid as first byte of an EBML number`. The first implementation of this scan counted only (1) and called a file with a 64 KiB hole clean — measured, in the test that now guards it. (3) A body that is simply absent: zero the packets of a 20 s file and libav returns one packet then a clean end-of-file, so only the shortfall against the header's own declared duration reveals that 20 s went missing. Corollaries: the scan runs in the crash-isolated worker, because its inputs are by definition malformed (V6); it is bounded against non-termination, since `PacketIter` yields `Some(Err(..))` and continues, so a demuxer stuck on an unparseable byte would return the same error forever without advancing; it is whole-file, because a head-only sample answers "clean" for a file that breaks two-thirds through and a health check that confidently passes a broken file is worse than none; and its cost is therefore bounded by MEMOISATION rather than by sampling — every verdict is recorded, CLEAN ones included, since a clean result leaves no trace anywhere else and recording only failures would re-read every healthy file on every pass. The verdict carries where the damage starts and the demuxer's own words for it, never a bare class (V133). Guards: libav_integrity.rs an_intact_container_scans_clean, a_hole_punched_mid_file_is_reported_with_its_position, a_wholly_shredded_body_terminates_rather_than_spinning; libav_pool.rs pool_scans_integrity_across_the_worker_boundary; integrity.rs a_body_that_stops_far_short_of_the_header_is_damage; integrity_memo.rs a_clean_verdict_is_remembered_not_just_a_damaged_one.

- V141: a shared init segment describes the timeline its fragments are SERVED on, and one init URL has exactly one body. Both halves are load-bearing and both were violated at once.
