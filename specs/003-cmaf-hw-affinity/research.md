# Research: hardware encoding for CMAF renditions

Phase 0 for [spec.md](./spec.md). Each item states the decision, why, and what
was rejected. Two of these overturn the shape the spec assumed.

---

## R1 — What identifies a rendition?

**Decision.** The rendition key is the `TranscodeOptions` that build both the init
and its segments, with the time fields (`start_position_ticks`, `duration_ticks`)
zeroed: item path, `video`, `container`, `video_bitrate_bps`, `audio`/
`audio_bitrate_bps`, `audio_source_stream_index`, `burn_subtitle_stream_index`,
`burn_subtitle_is_text`, `source_frame_rate`.

**Rationale.** `h264cmaf_init` and `h264cmaf_segment` both construct their options
through the same `fmp4_segment_opts(...)` call, differing only in segment index.
Anything that changes the encode's parameter sets is already in that struct, so
deriving the key from it cannot drift from what actually shares an init — a
hand-listed key would.

**Rejected.** Keying on `PlaySessionId`: two sessions on identical options can and
should share cached segments, and a session id would fragment the cache. Keying on
item id alone: too coarse — an audio-track or burn change is a different init.

---

## R2 — Wait for the pinned device, or start a new generation?

**Decision. Wait (queue on the pinned device). A new generation is NOT available
mid-stream.** The spec left this open; the code closes it.

**Rationale.** The media playlist is rendered whole, VOD-style, with a single
`EXT-X-MAP` (`init_uri`) covering every segment, and served
`playlist_cache_control(false)`. An HLS client does not reload a VOD playlist, so
there is no moment at which a new init URI could reach a player mid-playback.
"Start a new generation with its own init" therefore cannot be done without the
client restarting the stream — it is not a fallback the server can take
unilaterally.

**Consequence.** The degraded path is explicit rather than silent: if a pinned
device is in cooldown or fails, the segment request fails (5xx) rather than
spilling to another encoder. hls.js retries, and on a fatal error the player
reloads the source, which re-fetches the init and pins afresh. A visible stall
that recovers is the correct trade against silent undecodable video, which is
what issue #114 actually cost.

**Rejected.** Silent CPU fallback — that IS #114. Live-playlist rewriting to
introduce `EXT-X-DISCONTINUITY` + a second `EXT-X-MAP`: real HLS, but it converts
every VOD playlist into a mutable one and needs client reload behaviour we do not
control; far more blast radius than the problem warrants.

---

## R3 — The segment cache is device-blind, and that is a correctness hazard

**Decision.** The pinned device must participate in the on-disk segment identity,
and `HLS_GEN_VERSION` must be bumped when this ships.

**Rationale.** `HlsSegmentCache` paths are derived from the encode parameters and
carry no notion of which device produced the bytes. Today that is harmless because
CMAF H264 is CPU-only — every cached segment came from libx264. The moment a
rendition can be pinned to hardware, a cache populated under one pin can be served
under an init generated by another: exactly the mixed-SPS failure, arriving from
disk instead of from the load balancer, and surviving restarts. A stale cache from
the current CPU-only era would do this on the first deploy, which is why the
version bump is not optional.

**Rejected.** Leaving the cache alone and relying on the pin being stable in
memory: the cache outlives the process, the pin does not.

---

## R4 — Is a hardware encoder self-consistent across separate encodes?

**Decision. UNVERIFIED — this is the gate on the whole feature, and it must be
measured before any of it ships.**

**Why it matters.** Every segment is an independent encode (its own worker
invocation). The design assumes that two independent `h264_nvenc` encodes of the
same source with identical arguments emit byte-identical SPS/PPS. That is very
likely — the parameter set is a function of the settings — but it is precisely the
class of assumption issue #114 punished. `device_supports`'s comment establishes
that libx264 and hardware differ; it does not establish that hardware agrees with
itself across processes.

**How to settle it.** Encode two different segment windows of one source on the
same NVENC device, extract the SPS/PPS from each (`ffprobe -show_data` on the
extradata, or parse the `avcC`), and byte-compare. Repeat across a worker restart,
since a fresh process is the case that matters. If they differ, this feature is
dead in its current form and the CPU-only rule should stand.

**Rejected.** Shipping behind a config flag and watching production: the failure is
silent to the server and appears as unplayable video for the user.

-r 25` into fragmented MP4; `avcC` extracted and byte-compared.

```
nv_a.mp4         len=54 sha=b5b371b117b50dc1  014d4028ffe10027674d4028965280f004...
nv_a_repeat.mp4  len=54 sha=b5b371b117b50dc1  014d4028ffe10027674d4028965280f004...
nv_b.mp4         len=54 sha=b5b371b117b50dc1  014d4028ffe10027674d4028965280f004...
sw_a.mp4         len=46 sha=cc908eee14d60920  01640028ffe1001b67640028acd9407802...

nvenc same window, separate process : IDENTICAL
nvenc different windows             : IDENTICAL
nvenc vs libx264                    : DIFFER
```

**Verdict: a hardware encoder IS self-consistent across processes.** Two
independent NVENC encodes of different source windows produce byte-identical
parameter sets, so pinning a rendition to one device satisfies the one-encoder
requirement. The feature is viable and Phase 2 may start.

The control is worth as much as the result: NVENC emits Main profile (`0x4d`)
where libx264 emits High (`0x64`), 54 bytes against 46. That re-confirms the
#114 hazard on this exact hardware rather than taking the original comment on
trust — mixing the two under one init would hand the client the wrong SPS.

## R5 — Which device should a rendition pin to?

**Decision.** At init time, pin to the least-loaded eligible device by the existing
`eligible_for` priority (hardware first, CPU last). Whatever it picks is the
rendition's device for its lifetime.

**Rationale.** This reuses the placement policy already in `place()` rather than
inventing a second one, and it degrades naturally: if the GPU is saturated when a
rendition starts, that rendition runs wholly on CPU — correct, just slower, and
exactly today's behaviour.

**Open (sizing, not correctness).** NVENC advertises 8 sessions. Concurrent
renditions each hold affinity but permits remain per-job, so more than 8 busy
pinned renditions will queue on the GPU while CPU sits idle. On this deployment
(single household) that is not reachable; on a larger one it would need a
"pin only while headroom exists" rule. Out of scope, noted in `plan.md` risks.

---

## R6 — Does anything else share this hazard?

**Decision.** Gate on "shared-init fMP4", not on H264.

**Rationale.** The current rule is `H264 && Fmp4`. The hazard is a property of
shared-init fMP4 generally — the existing comment says as much ("H265 fMP4 would
carry the identical hazard, but no hevc CMAF rung exists today"). VP9 fMP4 already
exists and is CPU-only for a different reason (no NVENC VP9 encoder), so it is
unaffected in practice, but the affinity mechanism should key off the container
contract rather than re-encode the codec list.

## R7 — Can the encoders simply be made to agree? (measured 2026-07-28)

**Question.** If NVENC and a software encoder emitted the same SPS, no pinning
would be needed and free load-balancing could continue. Is the difference
reconcilable by flags, or by swapping libx264 for a different software encoder?

**Answer: no.** Measured on the deployment GPU, decoding the `avcC` SPS
field-by-field rather than trusting the original comment.

Defaults differ in profile AND in two internal derivations:

| field | NVENC | libx264 (default) |
|---|---|---|
| `profile_idc` | 77 (Main) | 100 (High) |
| `log2_max_frame_num` | 8 | 4 |
| `log2_max_poc_lsb` | 8 | 6 |
| High-profile fields | absent | present |

`-profile:v main` on libx264 aligns `profile_idc`, `constraint_flags`,
`level_idc` and removes the High-only fields — so most of the gap IS forceable.
The remaining two are not:

| encoder | log2_max_frame_num | pic_order_cnt_type | log2_max_poc_lsb |
|---|---|---|---|
| h264_nvenc (default) | 8 | 0 | 8 |
| h264_nvenc `-bf 0` | 8 | 2 | — |
| h264_nvenc `-g 16` | 8 | 0 | 8 |
| libx264 `-profile main` | 4 | 0 | 6 |
| libx264 `-g 256` | 4 | 0 | 6 |
| libx264 `-refs 4 -bf 0` | 4 | 2 | — |
| libopenh264 | 15 | 2 | — |

NVENC pins 8 regardless of GOP length or B-frames; x264 pins 4 regardless of
`-g`/`-refs`; openh264 is further away still (15, and poc type 2). No ffmpeg
flag moves either, and no available software encoder matches.

**Why it cannot be patched around.** `log2_max_frame_num` is the WIDTH of the
`frame_num` field in every slice header. Changing it in the SPS does not
re-encode the slices, so an init rewritten to "agree" would make the decoder
mis-parse every slice that follows. This is a bitstream-layout difference, not
a metadata one.

**Consequence for the design.** The one-encoder-per-rendition requirement is
real and cannot be dissolved. Pinning (this spec) stands as the fix. The one
useful by-product: `-profile:v main` narrows the gap enough that profile is NOT
the obstacle, so nobody need re-investigate that branch.

**Rejected.** Rewriting `avcC` to match (breaks slice parsing, above); swapping
libx264 for openh264 (further apart, and a large quality/speed regression);
hardware-only with no CPU fallback (that is pinning, minus the safety).

## R8 — A DETERMINISTIC device beats a pin map (design change, 2026-07-28)

**Decision.** Do not keep a `RenditionKey -> device` map. Choose the device as a
pure function of the rendition key over the devices that SUPPORT the encode.

```
pool   = hardware devices supporting opts, else [CPU]
device = pool[ rendition_key % pool.len() ]
```

**Rationale — it removes two hazards the pin map could not.**

1. *Restart.* An in-memory pin dies with the process while the on-disk cache and
   the client's already-fetched init both survive. A restarted server could
   re-pin a rendition to a different device and serve segments that no longer
   match the client's init — the #114 failure, arriving after a routine deploy.
   A pure function returns the same device after a restart, so there is nothing
   to lose.
2. *Cache identity (R3).* The reason the cache needed a device tag was that
   entries could outlive the pin that produced them. With a deterministic
   device, every cached entry for a rendition was necessarily produced by the
   device that rendition still resolves to. `HlsSegmentCache` needs no change,
   and `HLS_GEN_VERSION` need not be bumped — which also spares a full
   regeneration of the 40 GiB segment cache on deploy.

It is also simpler: no map, no eviction TTL, no lock, and no async pin lookup
from the cache layer (`SegmentKey` is built synchronously, so consulting a pin
map there would have meant an actor round-trip inside a sync path).

**Cooldown must not change the choice.** Cooldown is transient, so letting it
select a different device would reintroduce non-determinism through the back
door. The chosen device is computed IGNORING cooldown and load; if it is then in
cooldown the request FAILS (FR-004), and if it is merely busy the job QUEUES.

**Multi-GPU.** Hashing over the pool rather than always taking the first device
spreads renditions across GPUs while keeping each rendition on one. With a
single GPU it degenerates to "always that GPU", which is what this deployment
wants anyway.

**Known limitation, documented rather than hidden.** If the device TABLE changes
shape — a GPU added or removed — the function's answer can change for a
rendition whose cached segments predate the change. That is a physical hardware
change accompanied by a redeploy; bump `HLS_GEN_VERSION` at that point. Noted in
quickstart rollback.

**Supersedes.** The `RenditionPin` entity in `data-model.md` and the pin-map
tasks (T011-T013, T016) collapse into one pure function plus its tests.
