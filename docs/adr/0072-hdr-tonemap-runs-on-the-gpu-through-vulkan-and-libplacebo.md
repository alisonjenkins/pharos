# ADR-0072: HDR tonemap runs on the GPU through Vulkan and libplacebo, with the CPU chain as the fallback

- **Status:** Accepted
- **Date:** 2026-11-08T00:00:00Z
- **Deciders:** Ali

## Context

ADR-0070 maps HDR to SDR with a software `zscale`/`tonemap` chain on every re-encode and forces a software decode. On this machine (ali-desktop, 32 threads) that chain costs about 230 CPU-seconds for a 30 s 4K clip, so one 4K HDR stream holds several cores however fast the GPU encodes. Production is an AMD RX 9070 on Mesa (radeonsi, radv) in a Kubernetes pod; `tonemap_vaapi` returns ENOSYS on radeonsi and `tonemap_opencl` needs a runtime the image lacks (ADR-0070).

A benchmark showed a path that works on radv: decode with Vulkan (`-hwaccel vulkan`), tonemap with the `libplacebo` filter on the GPU, read the frame back (`hwdownload`), upload it to VAAPI (`hwupload=derive_device=vaapi`) and encode with `h264_vaapi`. Zero-copy `hwmap` from VAAPI to Vulkan fails with `VK_ERROR_INVALID_DRM_FORMAT_MODIFIER_PLANE_LAYOUT`, so the readback stays.

## Decision

- **Route.** `VaapiPipeline` gains `GpuTonemap`. The argv builder lowers it to `-init_hw_device vaapi=va:<node> -init_hw_device vulkan=vk@va -filter_hw_device vk -hwaccel vulkan -hwaccel_output_format vulkan -hwaccel_device vk` and the filter `libplacebo=tonemapping=bt.2390:colorspace=bt709:color_primaries=bt709:color_trc=bt709:range=tv:format=nv12,hwdownload,format=nv12,hwupload=derive_device=vaapi` (`Tonemap::gpu_filters`). `gpu_tonemap_argv_applies` is checked by the scheduler and again by the builder, so a job it rejects gets the unchanged CPU-chain argv whatever the caller asked for. It rejects: a non-VAAPI device, a stream copy, a filler window, shared-init fMP4, subtitle burn, and the per-eye/mono 3D filters. **Burn-in and per-eye jobs stay on the CPU chain** (libass and `overlay` need system-memory frames); moving them is a later change.
- **Capability.** At boot, for each VAAPI device, `probe_gpu_tonemap` generates a 256x144 10-bit HDR10 HEVC clip and runs it through the route's own argv. The verdict is a typed `GpuTonemapCapability` (`NotProbed` | `Capable` | `Incapable`) on the device slot; `NotProbed` reads as incapable. It is logged (with ffmpeg's last error line on failure) and published as `pharos_transcode_tonemap_gpu_capable{device}` (1/0). One trial covers the whole stack: Vulkan ICD, libplacebo in ffmpeg, Vulkan HEVC decode, VAAPI encode.
- **Selection.** The scheduler picks `GpuTonemap` for an HDR job whose source codec is HEVC (the codec the trial proves), placed on a device whose trial passed, when the argv applies and no earlier GPU attempt for the job failed. Any other HDR job keeps ADR-0070's chain and forced software decode. A second route (VAAPI decode, `hwdownload`, `hwupload` to Vulkan, libplacebo) was benchmarked at 22 to 32 fps for 4K with 4 to 7 CPU-seconds; it saves CPU but is slower than the CPU chain on a 32-thread machine, so it is not included.
- **Fallback.** A GPU run that fails with `device_unusable`, `decode_failed` or `other` is redone once on the CPU chain on the same worker, as the resident pipeline is; a worker death re-places the job on the CPU chain. Faults the CPU chain would share (`bad_input`, `io`, `unsupported_codec`, `no_frames`) are not retried. The retry is per segment: a systematic runtime failure costs one failed attempt per segment until a restart re-runs the trial.
- **Signals.** `pharos_transcode_tonemap_path_total{path=cpu|gpu}` counts HDR jobs per dispatch; `pharos_transcode_tonemap_fallback_total{reason=device_unusable|decode_failed|other|worker_died}` counts GPU runs redone on the CPU (only redos that are actually scheduled); both are created at zero at startup. `pharos_transcode_tonemap_total{tonemap,source_range}` is unchanged: it counts the request-time decision, made before a device exists, so it cannot carry a route label.
- **Packaging.** The `ffmpeg` binary the server spawns is `ffmpeg_8-headless.override { withPlacebo = true; }` (`ffmpegGpu` in `flake.nix`) in the devShell and on the OCI `PATH`. ffmpeg 9.0.1's libplacebo filter fails to configure against a Vulkan hardware device on radv ("Error initializing filters", EINVAL, no log line) while 8.1.x runs the identical graph, so the binary is 8.x; the libav libraries `ffmpeg-the-third` links, and its headers, stay on `ffmpeg-headless` 9.0.1. The OCI env sets `VK_ICD_FILENAMES` and `VK_DRIVER_FILES` to mesa's `share/vulkan/icd.d/radeon_icd.x86_64.json`, as `LIBVA_DRIVERS_PATH` is set for VAAPI, because the image has no FHS ICD directory. The pod needs `/dev/dri/renderD*` as before; Vulkan uses the same render node through radv.
- **Curve.** The GPU route uses BT.2390 and the CPU route keeps hable, and they are not aligned. Measured on the 30 s 4K HDR10 benchmark clip (60 frames, mean and max luma of the 8-bit output): CPU chain hable 105.6 / 169; libplacebo BT.2390 143.1 / 224; libplacebo hable 156.5 / 230; mobius 143.1 / 224. libplacebo's hable is not closer to the CPU chain than BT.2390 is. The gap is the reference white, not the curve: the CPU chain maps PQ with `npl=100` (SDR white at 100 nit), libplacebo maps diffuse white near 203 nit, which is the brighter look mpv and most players give. BT.2390 is the standard curve for this and is kept. The cost is that a title looks brighter on the GPU route than on the CPU chain, including for the single segments redone on the CPU after a GPU failure. Matching them would mean raising `npl` in ADR-0070's chain, which changes every CPU-tonemapped picture and is a separate decision.
- **Cache key.** GPU and CPU outputs share one cache entry: the route is not in `SegmentIdentity` (`_tm` stays the only HDR marker) and the capability is not in `DeviceTable::placement_fingerprint`. The route is chosen after the key is computed, so it structurally cannot split the cache. A distinct key would make the entry depend on a runtime verdict: a driver update or a missing ICD after a restart would flip it and re-encode every cached HDR segment (the thrash `placement_fingerprint` exists to prevent), while the two outputs feed the same `h264_vaapi` encoder the same NV12 and differ only in tone. Asserted by `gpu_tonemap_needs_a_passed_trial_and_stays_out_of_the_cache_generation`. Shared-init fMP4 renditions never take the GPU route, so one encoder pipeline still produces every segment of one init.

## Consequences

- Measured on the RX 9070 XT by running pharos's own argv for each route through `ffmpeg -benchmark` on the 30 s 3840x2160 30 fps HDR10 clip (900 frames, 15 Mbps HEVC10 in, `h264_vaapi` 15 Mbps out, machine shared with other builds): CPU chain 227 and 240 user CPU-seconds at 41.5 and 46.9 fps; GPU route 1.39 and 1.33 CPU-seconds at 83.8 and 83.5 fps. About 170x less CPU and about 2x the throughput.
- ffmpeg on `PATH` is 8.1.x while the in-process libav is 9.0.1. The spawned `ffmpeg` runs every segment, probe and image job; its other behaviour (zscale chain, encoders) is the same on 8.1 for the integration suite (`it_segments`, including `hdr_tonemap`) which passes against it. Moving the binary back to 9.x needs only the `ffmpegGpu` definition changed once the libplacebo filter works there.
- A box without Vulkan, without the ICD, or without Vulkan HEVC decode reads `Incapable`, logs the reason once and keeps ADR-0070's behaviour exactly.
- The trial and the route both depend on one Vulkan ICD per render node. A multi-GPU pod relies on `vulkan=vk@va` deriving Vulkan from the same VAAPI node.
- Not covered: HEVC is the only source codec proven (an HDR AV1 or VP9 source stays on the CPU chain); subtitle burn and 3D per-eye jobs stay on the CPU chain; there is no circuit breaker, so a trial that passes but a clip that fails costs one failed attempt per segment.

## Alternatives considered

- **Zero-copy VAAPI to Vulkan (`hwmap`).** Fails with `VK_ERROR_INVALID_DRM_FORMAT_MODIFIER_PLANE_LAYOUT` on radv.
- **`tonemap_vaapi` / `tonemap_opencl`.** Unavailable on radeonsi / no OpenCL runtime (ADR-0070).
- **VAAPI decode, readback, upload to Vulkan, libplacebo.** Less CPU than the CPU chain but slower than it at 4K here (see Decision).
- **Align the curves with libplacebo `tonemapping=hable`.** Brighter still, so it aligns nothing.
- **A distinct cache key per route.** Rejected above.
- **ffmpeg 9.0.1 with `withPlacebo`.** Builds, but the filter does not configure against Vulkan on radv.
